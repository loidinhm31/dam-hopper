# Application fixture feasibility

**Scope:** evidence for the frontend restructure described in `plans/reports/advise-261004-1527-frontend-test-evidence.md`. Research only; no implementation or checks were run.

## Finding

A genuine application E2E is feasible with the actual `apps/web/src/main.tsx` entry and production `dam-hopper-server`. **Final parent design:** reuse existing production Dockerfile's real built SPA/backend inside a fixture-owned application container plus separate isolated Mongo/private network; normal AuthStore/middleware and deterministic canonical data. Same-origin published app URL replaces host Vite for acceptance. Retain existing Vitest component/cross-layer suites. Details below record source seams, not authorization to use mock-auth or host-personal data.

The important precondition is home isolation: the production `AppState::new` does not necessarily honor `HOME` for Advisor data. `resolve_effective_home()` checks `/etc/dam-hopper/host.toml` for `service_user` first, then falls back to `dirs::home_dir()` (`server/src/api/agent_status.rs:71-88`); `AppState::new` passes that result to `AdvisorService` (`server/src/state.rs:431-434`). There is no observed production CLI/env override. A test must prove the effective Advisor path is its temp directory before reading or mutating policy/evaluation data; run in a disposable environment with controlled host config or provide a narrowly scoped test seam. `HOME`/XDG alone is not a sufficient safety guarantee on managed hosts.

## Isolated real-server fixture and external state

Launch the actual `dam-hopper-server` executable with explicit `--config`, `--workspace`, loopback `--host`, selected `--port`, and CORS origins for the Vite origin. The CLI exposes `--config`/`DAM_HOPPER_CONFIG`, `--workspace`/`DAM_HOPPER_WORKSPACE`, `--port`/`DAM_HOPPER_PORT`, `--host`/`DAM_HOPPER_HOST`, and CORS settings (`server/src/main.rs:35-57`). Never use `--no-auth`; leave it absent/false. Mongo is supplied by `MONGODB_URI` + unique `MONGODB_DATABASE`; startup constructs `AuthStore` and indexes when both are present (`main.rs:730-755`). Use a disposable Mongo container/database, no persistent volume, loopback-only published port, and remove it on every exit path. The local checkout has no local `mongod`; a container engine is the required Mongo prerequisite.

Set isolated `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME`, and `TMPDIR` before spawning the server. Also run from an empty temporary working directory and supply a controlled environment: startup loads a CWD `.env`, the global config `.env`, and config-adjacent `.env` (`server/src/main.rs:293-331,500-512,563-565`). Explicit `--config` and `--workspace` avoid discovery of a user's global/default workspace. Keep `session_db_path` explicitly under the run temp root (`server/src/config/schema.rs:241-242,639-641`; `main.rs:593-634`); the default is under `~/.config`. Isolate server token and OPAQUE setup under XDG config; startup creates/reads these (`main.rs:758-760,1012-1033`). Keep diagnostics, telemetry/session SQLite, workspace, agent-store, audit and any other config-selected state beneath the run root. Do not reuse the developer's Mongo database, config, credentials, cache, or workspace.

Create a complete temporary workspace: `dam-hopper.toml`, real project root directory, and any configured workspace/agent-store paths. Use the production config with Advisor initially disabled and a real `fixture-project` entry. Verify all resolved roots are in the run temp directory. `AppState::new` also initializes services outside the obvious config path: e.g. `CodexExporterManager::default_paths()` (`server/src/state.rs:418-419`) and the default Advisor home described above. Treat those as isolation checks, not as assumed temp-safe behavior.

### Mongo auth and browser profile

The normal middleware reads an active session and account from Mongo and enforces protocol, identity, session ID, `authVersion`, `credentialVersion`, unrevoked state, exact JWT/session expiration agreement, 30-day expiry and recent MFA freshness (`server/src/auth/policy.rs:98-175`). The app E2E need not exercise registration/login/MFA screens: create a valid persisted user/session in the throwaway database and seed the resulting v2 bearer token into a fresh browser context. This reaches ordinary `require_auth`/`require_admin`, unlike `--no-auth` or the example's mock service.

A practical flow is to call real `POST /api/auth/register` in the isolated server, then promote that newly created account to enabled/admin in the isolated `users` collection; registration deliberately creates disabled `User` role records (`server/src/api/auth.rs:458-500`). Insert an `AuthSession` in the `authSessions` collection (or via `AuthStore::create_session`, `server/src/auth/store.rs:31-42,346-354`) with current issue/MFA timestamps and matching versions. Generate `AuthClaims { v: 2, sub, sid, auth_version, credential_version, iat, exp }` whose `exp` matches the BSON session `expiresAt`, signed with the fixture server-token bytes; `AuthClaims::encode` is available (`server/src/auth/model.rs:137-164`). Avoid the interactive auth UI entirely, while still verifying a missing/invalid token is rejected and the seeded session is accepted by the normal auth middleware. Never print or attach the signing key/token to reports.

Seed the documented normal browser storage keys from `packages/ui/src/api/server-config.ts:14-16,51-62`: one UUID-v4 profile at `damhopper_server_profiles`, active profile ID at `damhopper_active_profile_id`, and `damhopper_profile_auth_v2_<profile UUID>` containing `{version:2, serverUrl:<normalized Vite origin>, authType:"basic", token:<v2 JWT>}`. The profile should be `authType:"basic"`, `autoConnect:true`, and its URL should equal the frontend origin; the v2 token record is endpoint-bound and is discarded if that URL/auth type differs (`server-config.ts:290-320,334-349`). This lets the normal startup profile restoration perform `/api/auth/status` and WS auth. Seed no other client storage.

### Deterministic model discovery boundary

The production `HarnessModelService` calls four external executables from `server/src/advisor/models.rs`: `omp models ls --json --no-extensions`, `pi --offline --list-models --no-extensions`, Codex app-server JSONL (`initialize`, `model/list`), and Claude stream-json initialization (`models.rs:649-933`). The registered `HarnessCommandRunner` is the external-process boundary; the in-process `FakeHarnessCommandRunner` used in server tests cannot be injected into the ordinary running production server without adding a configuration seam.

Protocol-correct fixture CLI shims can exercise harness-specific discovery at the external-process boundary without mocking app APIs. **Initial confirmed theme/persistence journey does not require harness-specific catalog execution:** parent chooses real built-in fallback with discoverable CLIs absent from controlled production image/PATH; API route, fallback normalization and selector remain real. Do not call local provider CLIs, copy model blobs and pretend they are wired, or label fallback as harness success.

## Readiness, lifecycle, and evidence policy

The production binary logs “Listening” before it binds (`server/src/main.rs:920-923`), and port `0` is not usable as a ready address because the log reports configured port before `local_addr` is available. Select a loopback port and treat a successful `/api/health` response as HTTP readiness (`server/src/api/router.rs:72`); capture early server exit/bind errors and do not treat the startup log alone as readiness. Then use authenticated `/api/auth/status` and `/api/advisor/status` checks to prove the seeded principal is a current admin and the reported Advisor path is the expected temp home. Validate model/evaluation readiness from real APIs before launching the browser scenario. Start Vite with strict-port behavior and wait for the frontend response before navigation.

Improve fixture lifecycle relative to the current Vitest browser plugin (`packages/ui/vitest.advisor-routing.browser.config.ts`): it can launch a prebuilt example or Cargo wrapper, uses fixed dev port 15174, buffers readiness stdout without a bound, has no ready timeout/post-ready process monitor, and cleanup sends stdin EOF/SIGTERM without awaiting exit or escalating. A child Cargo wrapper is not necessarily the server process tree. The example itself supports stdin EOF/interrupt/SIGTERM and Axum graceful shutdown (`advisor_routing_browser_fixture.rs:92-116,232-234`); production main handles SIGTERM/ctrl-c and has a bounded HTTP drain plus managed subsystem shutdown (`main.rs:932-1000`). For app E2E: close browser/WS first; SIGTERM Vite and server, await each exit, escalate after a bounded deadline and fail on forced termination; drain/capture stdout and stderr continuously; monitor post-ready exits; then remove temp roots and stop/remove the unique Mongo container/database on all setup/test failure paths. Leave no server, Cargo child, Vite process, Mongo container, or persistent volume behind.

The accepted evidence split remains: retain useful Vitest browser components; add genuine Playwright Test flows over the real app for privacy, route editor, and evaluations; CI asserts behavior without generating images. Local visual review uses a fresh complete application viewport capture for each relevant state and a human review. Store captures outside `plans/` (no images in the plan directory), and do not make local screenshot generation a CI requirement. Existing hard-coded component screenshot paths should not become the app evidence destination.

## Resolved design decisions / remaining execution prerequisites

1. **Effective Advisor home:** production app container with controlled `/etc`, no host-home mounts; assert reported root under `/e2e/home` before domain operations. No production test-only home override.
2. **Privacy visual target:** actual selectable Heavy Blur. No new Moderate Blur feature.
3. **Bound port:** fixed internal port 4800, engine-assigned host loopback publication; real HTTP/auth/root readiness, not pre-bind log or production port 0.
4. **Local prerequisites:** Docker-compatible rootless Podman is reachable (`docker info` observed); image builds/container startup not exercised in planning. No local mongod needed; owned Mongo container mandatory, no mock fallback.
5. **Authentication/catalog:** real database session seed using canonical Rust types; normal persisted frontend profile/auth bootstrap. Login/MFA and harness-specific discovery remain explicitly uncovered workflows.

Unresolved questions: none blocking design. Implementation must exercise current-source container build, actual journeys, cleanup and fresh human-reviewed evidence; this report claims source feasibility only.
