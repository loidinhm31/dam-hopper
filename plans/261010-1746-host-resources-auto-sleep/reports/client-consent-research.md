## Proposed content-free presence registry
- In-memory records: opaque socket ID, capability digest, authenticated session/subject binding, auth/credential versions, deadline, connected/liveness metadata; registry has membership revision. No terminal IDs, terminal bytes, prompts, command arguments, filesystem paths, IPs, raw JWTs or agent outputs; public projection only counts/phase facts. Auth binding remains server-private.
- Each **admitted public `/ws` connection** counts, including old clients and authorized non-browser public clients; this conservative classification cannot exclude a quiet/old UI. Count actual live sockets, not identities/tabs/profile intent or visibility. Reporter collector and resource streams excluded by registration seam.
- Create an RAII guard once upgrade actually runs; release exactly once on reader EOF/error/Close, writer failure, heartbeat failure, auth cancellation, task cancellation/panic and server shutdown. Writer must signal shared cancellation; registry invalidates capability as soon as closing starts, then tears down tasks deterministically.
- Recommended liveness policy: server Ping every 30s with bounded nonce; matched Pong within 90s, monotonic deadline; browser auto-Pong avoids requiring new JS heartbeat support and keeps hidden/old tabs counted. Pong proves transport presence, **not** consent or free agent state.
- On heartbeat/write failure, cancel and remove only that exact socket generation. Until definitive lease expiry/removal, ambiguous connectivity remains presence; do not treat missing event traffic as zero clients.
- Supervise liveness independently of long FS/request handlers: current reader awaits dispatch work. Avoid timing out a busy healthy socket because application handling delayed Pong consumption; arrange bounded reader/control processing before adopting deadlines.
- After subscribe/register, send **only that socket** a `host:uiConnection` receipt: `{version:1,connectionId,decisionCapability}`. Fresh high-entropy capability per socket; digest retained server-side. Never broadcast receipt through `event_sink`, put capability in GET/global status, persist it, or log it.
- `WsTransport` retains receipt in memory for its exact socket/generation, exposes subscription/current receipt, clears on close/destroy/reconnect before any decision. Ensure initial receipt cannot be lost before bridge/overlay subscribes (transport stores snapshot).

## Authoritative status and HTTP contract
- Keep existing public v1 top-level coordinator states; add semantic eligibility/consent phase fields rather than a second versioned status endpoint. Main coordinator defines fixed `agent-free` startup policy and read-only quiet period 10800s; automatic RTC wake stays existing timing value.
- Protected GET status adds nullable consent object `{requestId,requestRevision,phase,openedAtMs,deadlineMs,hasApproval}` plus aggregate UI connection count and safe reason. No participant identities/capabilities. Display timestamps are wall-clock facts only; monotonic clocks authorize transitions.
- `requestRevision` is immutable issuance/free-epoch revision, **not** ever-changing `statusRevision`: another approval/status refresh must not invalidate a concurrent valid No. Request ID includes server-instance freshness (random UUID sufficient); restart loses request/capabilities and starts conservative new observation period.
- Proposed POST `/api/system/idle-suspend/v1/consent/decision`, bounded JSON body: `{requestId,requestRevision,connectionId,decisionCapability,decision:"approve"|"deny"}`. No client `sessionId`, username, `profileId`, wake timing or force flag on wire.
- Guards: protected `require_auth`, existing JSON/cookie-Origin guards, production enabled actor, then exact active registry record + capability + actor subject/session/version match + deadline; reevaluate submitting session at admission. Any enabled authorized user's eligible socket may approve; no administrator/unanimity requirement, no reporter capability substitution.
- Invalid shape/capability never reaches coordinator; generic 403 binding failure; 409 for stale/closed request and `handoffInProgress` after commitment; successful valid receipt returns authoritative outcome/revision, always no-store. Authentication unavailable remains fail-closed, not fake denial or approval.
- Transport timeout or lost response is **not** an answer. Do not retry decision POST automatically; reconcile GET and let deliberate user action resubmit. Repeated same decision for same request/socket is idempotent; a later valid deny before commitment always overrides its previous approval.
- Capture exact owner, request/revision and receipt when rendering/dispatching; mutation binds that owner API. Never resolve active profile at click/response time. Discard results after generation/request replacement; abort on owner invalidation. Client profile IDs never sent as host policy facts.

## Finite consent lifecycle and race rules (recommended 60s window)
1. Agent-free means Idle + Blocked; Working, Unknown, stale or incomplete coverage blocks and clears continuity. Require **more than** 10800 monotonic seconds continuous qualified free; no quiet-terminal completion inference. Semantic eligibility supplier belongs to sibling/main design.
2. At qualified deadline, capture registry membership revision. Zero UI sockets permits automatic final check/helper path; positive count creates one 60s consent request and broadcasts existing revision hint. Nonempty membership alone never resets free anchor when no request exists.
3. One valid authorized approval sets `hasApproval`; retain remaining short 60s window to allow concurrent No. Other users/tabs' silence **does not veto** that approval: user chose any approval, not unanimity. With no valid approval, whole request is unanswered.
4. Any valid deny accepted before atomic handoff cancels request immediately, discards approval and restarts free wait at denial time: another **>3h** qualified-free interval. At deadline with no approval, same reset at timeout. UI dismissal/Escape/outside-close maps to explicit deny when connected; network/unmount is never approval.
5. Joins during prompt receive current receipt then GET same request; do not renew deadline/create parallel request. New socket may answer if its actor/session/capability checks pass. Membership revision invalidates final presence ticket but does not automatically deny.
6. Disconnecting a socket invalidates its capability and any uncommitted approval attributed solely to it; another live valid approval remains sufficient. **Last disconnect during prompt cancels and defers another full >3h**, never converts unanswered prompt into no-client immediate sleep. Close/auth/heartbeat/reload cannot manufacture consent.
7. Reload/reconnect creates fresh socket receipt; stale decisions fail even if login session survives. If other sockets kept request alive, refetch and re-prompt same request; prior socket capability never migrates. Last-socket reload gets cooldown under rule 6. Old clients count but cannot approve without receipt/API support; no new-client answer => timeout/reset.
8. At 60s deadline with approval, fresh semantic eligibility and current UI/auth conditions must pass before atomic handoff. Serialize join/leave, deny, deadline, policy/timing changes and handoff claim against request/free epoch + presence ticket; **deny accepted before commitment wins**, after commitment return `handoffInProgress` and never claim cancellation succeeded.
9. A joining socket racing no-client final check invalidates that ticket and forces prompt before commitment; after helper commitment, arrival cannot undo accepted suspend. No asynchronous gap between checking revision and claiming automatic handoff.
10. Working/Unknown/stale, disable/manual handoff, changed relevant policy/timing or shutdown cancels uncommitted request/approval; restart continuity conservatively. Manual force stays an independent path and may intentionally override work under its existing confirmation/admission rules. No consent failure invokes helper.
11. Helper execution uses current automatic RTC wake setting, never POST payload wake overrides; exactly one automatic execution per claimed request/free epoch. Failed/suppressed attempts must not reuse approved stale request (main owns next eligibility cycle).
