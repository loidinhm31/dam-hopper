### Credential-baseline and Save-ownership contract
This is a small component-local general credential guard, owned by `detach-dialog-devices`, not a device state machine or resurrected callback.
1. Bind initialized credentials and each accepted successful login/MFA result to `{profileId, normalized endpoint, tested baseline token}`, plus authType, request/incarnation identity and connection generation where available (capture legacy scope/new-profile incarnation explicitly). Record the successful verification's returned candidate and captured persisted baseline; a pending challenge or text edit alone grants no fresh-auth authority. Reuse existing `getAuthToken`/`setAuthToken`/`clearAuthToken`, with no duplicate token-store abstraction. Preserve request-ID, close/reopen, URL/profile and late-result fences. Never resolve the Save target anew through ambient profile after an await.
2. Before Save has side effects, compare that ownership/baseline with current persisted credentials and target. A copied/previously validated A is not saveable after A disappears or changes. A different non-null external token B always invalidates the draft, including a verified MFA draft; never silently rebase onto B. Deleted/retargeted profiles or unrelated generations also fail closed. Keep legitimate new-profile, no-auth and URL-change flows; neither stale ownership nor missing target permits ambient fallback.
3. Fresh authentication is not permanently poisoned by prior self-revocation. If the same dialog attempt successfully obtained a distinct new session credential, it may begin Save after the prior A is already retired and current storage is null for that same target. This includes verification completed before ACK and challenge completed after ACK (current 202–217). Admit only a genuinely new verified candidate, never A; reconcile an expected prior-owner retirement using available target/generation fences, not a device callback. Reject a non-null replacement B or unrelated owner change. At admission capture the actual current persisted token/generation as the Save baseline.
4. Once Save starts, freeze candidate, owner and baseline for that operation. Check before Save, after every media-cleanup await, before each credential clear/write, and before success publication/parent notification/disconnect/reconnect or legacy reload scheduling. Only this Save's successful metadata/credential transitions may advance expected endpoint/authType/token/generation: `getAuthToken` can return null after an owned URL/authType update, and token writes/clear attempts notify profile/connection listeners synchronously. Recheck actual storage/runtime owner after notifications, including failed/partial clear; a boolean alone does not prove ownership. Preserve legitimate URL-change/no-auth flows without treating their owned transitions as external or accepting a notification's external B. ACK retiring A during the await invalidates the operation even if its fresh candidate could have been saved by a separately begun post-ACK Save. Never rebase or auto-retry an in-flight Save.
5. Rollback is ownership-qualified too: restore the prior credential only while the same target still contains this Save's expected last-owned value and no external retirement/replacement/generation change intervened. Do not run unconditional old-token restoration on ownership loss or persistence failure; never clear/replace B or resurrect A. Preserve ordinary persistence-error restoration when still owned, URL-change token clearing and profile/legacy media cleanup ordering. Do not broaden whole-profile/active-profile restoration over another flow's changes; restore only still-owned affected state.
6. On lost ownership, stop remaining credential/runtime/success work and return failure with an actionable reauthenticate/retest message (no token values). No “Saved!”, parent success callback, automatic close, reload or stale reconnect. Do not erase a newer challenge/credential/error from another incarnation. Storage/cleanup failures remain actionable, and existing logout/Browser-reset fencing remains intact. No hard-coded legacy guard name/error string is required.
7. Distinguish pre-Save recovery from in-flight invalidation in tests: stale A fails; fresh post-retirement login/MFA succeeds; external B survives; deferred ACK during media cleanup leaves null or B unchanged with stable generation/socket count and no success; failed-persistence rollback cannot restore a retired credential or overwrite a concurrent replacement. Preserve endpoint/profile/incarnation/available-generation fences and unrelated ambient credentials in every case.
