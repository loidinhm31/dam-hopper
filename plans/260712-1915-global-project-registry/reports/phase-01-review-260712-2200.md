## High Priority Findings

### 1. Symlink bypass for explicit config validation
**File:** [server/src/config/resolve.rs](../../../server/src/config/resolve.rs#L75-L77)  
**Severity:** High (security boundary concern)

```rust
if let Some(path) = input.explicit_config {
    return load_config_at(&path, ConfigSource::ExplicitConfig);
}
```

`--config` flag accepts arbitrary paths without canonicalization or symlink resolution. User could provide `--config ~/safe/link.toml` where `link.toml -> /etc/passwd` or similar. While `read_config()` eventually canonicalizes, the initial validation happens after symlink resolution.

**Impact:** Phase 02 will allow absolute project paths. If user provides a malicious symlink as config, projects could reference arbitrary filesystem locations.

**Recommendation:** Canonicalize explicit config path before loading, validate it's within expected directories (e.g., no `/etc`, `/root`). Add test: `resolve_explicit_config_rejects_symlink_to_system_dir`.

### 2. Missing global registry path validation
**File:** [server/src/config/global.rs](../../../server/src/config/global.rs#L22-L24)

```rust
pub fn global_registry_path() -> PathBuf {
    dam_hopper_config_dir().join("dam-hopper.toml")
}
```

`dam_hopper_config_dir()` trusts `XDG_CONFIG_HOME` env var without validation. Malicious env could set `XDG_CONFIG_HOME=/tmp/evil` causing server to load attacker-controlled config.

**Impact:** Medium. Local environment compromise required, but consequence is arbitrary code execution via project commands.

**Recommendation:** Validate `XDG_CONFIG_HOME` is absolute, not world-writable, and within user's home. Fallback to `~/.config` if invalid. Log warning on env override.

### 3. Obscure config parent resolution
**File:** [server/src/config/resolve.rs](../../../server/src/config/resolve.rs#L145-L155)

```rust
fn config_parent(config: &DamHopperConfig, fallback_root: &Path) -> PathBuf {
    config
        .config_path
        .parent()
        .map(Path::to_path_buf)
        .unwrap_or_else(|| {
            fallback_root
                .parent()
                .unwrap_or(fallback_root)
                .to_path_buf()
        })
}
```

Logic is difficult to trace: when does `config.config_path.parent()` fail? Why does fallback need double parent resolution? No test coverage for the fallback branch.

**Impact:** Low. Likely dead code, but unclear behavior in edge cases.

**Recommendation:** Simplify or add doc comment explaining when fallback triggers. Add test for root-level config file (e.g., `/dam-hopper.toml`).

## Medium Priority Improvements

### 4. Redundant ConfigResolutionInput fields
**File:** [server/src/config/resolve.rs](../../../server/src/config/resolve.rs#L42-L50)

`ConfigResolutionInput` struct wraps 5 fields, but 3 come from global config and 1 is constant (`registry_path`). Only `explicit_config` and `workspace_dir` vary per invocation.

**Recommendation:** Consider builder pattern or two separate functions: `resolve_with_explicit_config()` and `resolve_with_defaults()`. Current design is fine for Phase 01 but may scale poorly when Phase 04 adds per-project validation.

### 5. Error handling inconsistency
**File:** [server/src/config/resolve.rs](../../../server/src/config/resolve.rs#L83-L94)

Explicit workspace with missing config returns `EmptyFallback` with warning (soft error). Explicit config with missing file returns hard error. This inconsistency is intentional but not documented.

**Recommendation:** Add doc comment to `resolve_startup_config()` explaining error vs. fallback policy per source type.

### 6. No protection against config path confusion
**File:** [server/src/main.rs](../../../server/src/main.rs#L94-L104)

User could provide both `--config` and `--workspace`. Current code prioritizes `--config` silently. User may not realize `--workspace` is ignored.

**Recommendation:** Return error or log warning when both are provided: "Both --config and --workspace provided; using --config and ignoring --workspace."

## Low Priority Suggestions

### 7. Test isolation for environment variables
Tests use `registry_path` arg but don't verify `DAM_HOPPER_CONFIG` env var works end-to-end. Environment pollution risk in CI.

**Recommendation:** Add integration test using `temp_env` crate or similar to test env var isolation.

### 8. Missing Windows path tests
Phase doc mentions "Windows Paths" in Phase 06, but resolver code doesn't explicitly handle Windows UNC paths or drive letters. `Path::is_absolute()` works cross-platform but not tested.

**Recommendation:** Defer to Phase 06 as planned. No immediate action.

### 9. Logging verbosity
`main.rs` logs config source, path, workspace name, and project count on startup. Helpful for debugging but potentially noisy in production. Consider `debug!` level for source/path, `info!` for workspace name only.
