## Requirements
- Exactly `profileQueryKey(owner,'system','resource-snapshot')` and `profileQueryKey(owner,'system','metrics')` remain consumer keys; no parallel shadow copies, no active-profile/client fallback for owner routes. Fetch and REST alert-history remain existing endpoints; no profileId wire field.
- REST snapshot at 15 s for connected/visible/interested owner only while `canUseResourceRest(owner,qc)`; compatibility metrics at **5 s only in visible detail**, subject to the same gate. No resource polls when hidden, disconnected/offline, paused, LIVE, switching or auth-blocked (including retry STARTING). Alert history at 30 s while visible and not auth-blocked, WS invalidations burst-coalesced; unchanged idle-suspend status and force-sleep policies.
- Handshake `STARTING` remains REST sole writer **until switching begins**. Valid full paired status+data (matching epoch/revision) synchronously publishes switching and source fence, then cancellation+atomic double cache write; `LIVE` rejects REST and WS resource cache writes. Status/heartbeat alone never grant authority/freshness; a reconnect's equal-revision first full pair with a new adjacent status is valid. On leaving LIVE, fence first then one owner/QC REST catch-up only if shared predicate permits.
- Presentation freshness: server ages since real observations + elapsed `performance.now()`, TTL from matched status, explicit section availability; TanStack `isStale` is request-cache metadata only. Periodic newer revision does not freshen older data; same-revision status may age/expire data without a new snapshot.

## Architecture
- Same `ConnectionRef` + **QC identity** is the single arbiter. Phase03 exposes `getHostResourceSource(owner,qc): {mode: SourceMode; sourceGeneration: number; switching: boolean; freshness: ProjectionFreshness}`, `captureResourceSource(owner,qc): number`, `isResourceSourceCurrent(owner,qc,sourceGeneration): boolean`, and `canUseResourceRest(owner,qc): boolean`. The last gate means current connected owner/exact registered QC/visible interest + `STARTING|RETRY_WAIT|REST_ONLY` + `!switching` + no persistent auth-blocked latch. Every snapshot/metrics REST start and post-await resolution checks that gate **and** captured sourceGeneration/current connection/QC; WS snapshot patch/invalidate/catch-up uses the same gate before any cache mutation/request, including microtask drain. Pass TanStack `signal` through `ApiClient.system.{resourceSnapshot,metrics}(signal?: AbortSignal)` to `transport.invoke(channel, undefined, {signal})`. Aborting alone does not fence noncooperative REST.
- Entering LIVE: decoder validates *both* DTOs and fresh adjacent status; coordinator synchronously publishes `switching:true` and increments sourceGeneration **before any await or query cancellation**, so independent observers/WS see the fence immediately. Cancel `{exact:true}` owner snapshot + metrics TanStack queries (signals reach transport); recheck owner/QC/attempt/new fence after each await; only then one `notifyManager.batch` writes two exact owner keys from the same decoded pair and publishes `LIVE`, `switching:false`. Never re-enable REST or WS writes between these steps. Failed/canceled switch fences stale REST responses and only its current attempt may release its flag to a permitted fallback/blocked/paused mode; stale attempt's `finally` must not clear a newer switch. Data missing immediately preceding matched status fails protocol; an equal-revision first baseline of a new attempt with new adjacent status is accepted, within-attempt duplicate/older rejected and any older-than-last-consumed same-epoch frame rejected.
- Leaving LIVE: abort stream/reader/timers and fence attempt + increment sourceGeneration **before** REST enable; old stream and REST responses cannot write. On visible REST-allowed `RETRY_WAIT/REST_ONLY/STARTING`, schedule one catch-up invalidate/refetch for snapshot and conditional detail metrics per owner/QC **only when `canUseResourceRest` holds at scheduling and execution**; dedupe observer demand and WS invalidations. `PAUSED` holds last known without network; resume retains retry budget and auth latch. `AUTH_UNAVAILABLE` from STARTING or LIVE immediately sets persistent auth-blocked latch, increments source fence and cancels both exact owner resource queries before any next I/O; visible mode remains `AUTH_BLOCKED` through retry fetch/status-only, hidden mode is `PAUSED` with latch retained and resumes to `AUTH_BLOCKED`. Only current authenticated full paired handoff to LIVE or explicit new connection generation clears latch; exhausting retries remains blocked. History REST checks visibility and mode `AUTH_BLOCKED` (never fetch during PAUSED); `STOPPED`/offline keeps last known without streams/polls.
- Freshness model per consumed `{serverEpoch,revision}` in coordinator, **not** copied to TanStack `dataUpdatedAt`. Matched pre-data status sets server ages/null and monotonic receipt time; local one-shot TTL expiry triggers mode-derived presentation notification without network/sampler read. Same-revision periodic status may only increase elapsed observation age; a newer/different-epoch periodic status is informational until its own validated full data is consumed. On fallback clear SSE freshness authority; use snapshot's explicit availability and existing last-known/error presentation conservatively, never treat REST promise resolution, sampledAt on a degraded revision, `isStale`, `200` or heartbeat as proof of successful observation. Preserve coarse process/PSS `sampledAt` and availability; no exact PSS age inferred.

## Risk Assessment
- Source-generation check without transport signal still allows unnecessary REST I/O; require both. TanStack cancellation alone does not reliably stop noncooperative promises; check before query resolution and after every awaited integrator step. Live cache writes that race with WS invalidations or ambient keys would re-poll host; gate both paths.
- UI rendering on a heartbeat or status receipt must not imply successful observation; set one monotonic expiry notification and keep existing availability granularity. Many profiles over one HTTP/1.1 origin can contend for connections; phase05 measures deployed proxy and native separately. No extra sampling worker or frontend-fabricated freshness.

## Security Considerations
- Exact owner+QC+attempt+source fence before **every** query completion/cache write; profileId is local key, not SSE wire data. `AUTH_UNAVAILABLE` retains credentials/WS but blocks snapshot, metrics and history REST until current authenticated paired full-data handoff or new connection generation; unknown 401/403 never alters token. No cookie/query token; sensitive host data stays in owner-keyed cache, never copied to global unqualified keys. ForceSleep and idle-suspend authorization untouched.
