# Host-resource SSE: transport and security research

**Research date:** 2026-09-29  
**Exploratory research; not the frozen contract:** [Authoritative host-resource SSE architecture](../../../docs/architecture/host-resource-sse.md) supersedes the earlier cookie/EventSource branch, poll-only fallback, `N/5` *lookup* estimate (actual persisted DB reads ≈`2N/5`), body-polled auth timer, and guessed per-section freshness cutoffs. The selected design uses bearer Fetch, independent auth supervisor, dual snapshot/metrics cutover, and a precisely correlated status immediately before each data frame. Scope: host-resource delivery only; no general event platform. Proposals below are not measured capacity.

## Findings and ranked choices

1. **Server: Axum/Tokio `watch` over the existing startup-owned monitor.** `axum 0.8` includes `response::sse::Sse`, `Event` and `KeepAlive`; `tokio` is `full`; `futures-util` and `tokio-stream` (`sync`) are present. No new crate. The selected bounded shared `Bytes` frame can use `Body::from_stream` without per-client `Event::data` snapshot copies. Keep collection startup-owned; never sample or serialize full JSON per connection. ([Axum SSE](https://docs.rs/axum/0.8/axum/response/sse/index.html); [`server/Cargo.toml:49-56,93-95`](../../../server/Cargo.toml))
2. **Browser: bearer-authenticated Fetch streaming, not native `EventSource`/cookies.** `EventSource` exposes URL and `withCredentials`, not an Authorization header; never place bearer tokens in URLs/query strings. Captured owner-bound Fetch uses `Authorization`, `credentials: "omit"`, `AbortController`, response reader, and a bounded feature-local parser/reconnect loop. Native targets without cancellable authenticated streaming Fetch retain REST. Cross-origin Authorization requires exact allowed Origin and preflight policy, plus explicit server-side Origin rejection for the actual GET. ([WHATWG EventSource interface](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-eventsource-interface); [Fetch Standard: Headers](https://fetch.spec.whatwg.org/#headers-class); [Fetch API](https://fetch.spec.whatwg.org/#dom-global-fetch))

## Protocol, reconnect, and retention

- Send `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: private, no-store, no-transform` (sensitive host data must not be cached), and `X-Accel-Buffering: no`. Do not emit `Connection: keep-alive`: HTTP/2 prohibits connection-specific fields. SSE messages end with a blank line; comment lines are ignored by the browser and can keep intermediaries active. ([HTML SSE format](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation); [RFC 9113 §8.2.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.2.2))
- Send **full atomic snapshot+legacy metrics** envelopes, not deltas. On admission send initial status then current cached data (after one publisher encode if needed), followed by latest revisions. No `id:` or `Last-Event-ID` replay: EventSource's reconnect protocol cannot provide history from `watch`; every reconnect receives current authoritative state, not gapless events. Dual-query REST snapshot/metrics own data until validated first SSE data; then SSE sole writer, both queries cancelled/fenced, with REST fallback on exit. ([WHATWG reconnect and Last-Event-ID](https://html.spec.whatwg.org/multipage/server-sent-events.html#reestablish-the-connection); [Tokio `watch`](https://docs.rs/tokio/1/tokio/sync/watch/index.html))
- `watch` retains only its latest shared encoded frame; receivers track seen versions. Explicitly read/send the current frame at connect; use `borrow_and_update()` after `changed().await` with a short borrow and no await to avoid duplicate/missed updates. One publisher performs **no new encoding** while interest is zero and retains at most one cached encoded frame; reuse if current revision unchanged on renewed interest, else encode latest **once**. A slow reader skips intermediate frames, not already queued bytes. Before **each** selected data frame, encode a separate small status from that frame's captured metadata and revision at actual emission; no per-client snapshot serialization. ([Tokio `watch`: retention and borrow/update](https://docs.rs/tokio/1/tokio/sync/watch/index.html#borrow_and_update-versus-borrow))
- Watch bounds application backlog, **not** Hyper/socket/proxy bytes or a stopped reader. No detached per-subscriber collector. Independent auth supervisor revokes new emission even under backpressure, but cannot guarantee wire-close/error delivery or recall bytes already queued. Response-body Drop releases slots and cancels supervision; browser aborts Fetch and reader on owner/profile/token/generation/unmount change, fencing late callbacks. `EventSource.close()` is relevant only as background API research, not the chosen transport. ([WHATWG EventSource `close()`](https://html.spec.whatwg.org/multipage/server-sent-events.html#dom-eventsource-close); [Fetch abort](https://fetch.spec.whatwg.org/#abort-fetch))

## Authentication and connection lifecycle

- Authenticate **before committing SSE headers**; unauthorized requests get finite errors. Use existing signed bearer policy only, with no cookie/query/event-ID credentials. Preflight uses existing outer CORS policy without taking a feature permit; actual GET traverses **global permit (32, before expensive auth) → explicit present-Origin validation → 2 s auth-work cap → existing `require_auth` → feature bearer check → per-subject permit (4) → handler**, with reverse Axum layer-wrapping order. Validate present Origin against existing exact same-origin/allowlist policy before auth; CORS response headers alone do **not** block server execution or admission. Absent Origin is allowed for authenticated CLI; no-auth dev mode still rejects disallowed present Origin. Never trust arbitrary forwarded origin/host headers.
- Independently supervised long streams evaluate signed claims with existing persisted session **and user** policy every **5 s** (typically two DB reads/check), bound each check to **2 s** and fail closed on revocation, expiry, version change, MFA requirement or store failure. Also arm independent already-known MFA/absolute expiry deadlines. Lease/cancellation gating checks immediately before **every** emission, including initial data and heartbeat, rather than relying on body polling, which stalls under backpressure. The 5 + 2 s cutoff is a scheduling goal for **new emission**, not a network guarantee: bytes already queued cannot be recalled and a backpressured body may not deliver EOF/error control. Keep the existing 10-day MFA step-up and 30-day absolute expiry policy. ([Baseline: live WebSocket session checks; RFC 9113 §10.5 DoS considerations](https://www.rfc-editor.org/rfc/rfc9113.html#section-10.5))

## Keepalive, freshness, proxy, and overload

- Proposed heartbeat: Axum comment keepalive every **15 s**; it is transport liveness only, never a host sample and never evidence metrics are fresh. Require every proxy/LB idle-read timeout to be **≥45 s** (3× heartbeat); configure NGINX `proxy_buffering off` for this route (or honor `X-Accel-Buffering: no`) and bypass response compression/transformation on SSE. Compression/buffering can delay small chunks; verify the deployed proxy/CDN, because repo dependencies do not define that path. ([Axum `KeepAlive`](https://docs.rs/axum/0.8/axum/response/sse/struct.KeepAlive.html); [NGINX `proxy_buffering`](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering); [NGINX gzip](https://nginx.org/en/docs/http/ngx_http_gzip_module.html))
- Preserve monitor cadences and budgets: default light **5 s**, processes **15 s**, PSS **60 s**, ≤250 ms jitter; process cooperative deadline **150 ms**, snapshot wait **500 ms**. Status at least every 15 s, plus immediately before **each** chosen data event with no interleaved control, computes monotonic `snapshotAgeMs`/`metricsAgeMs` from that frame's captured successful-observation instants and same epoch/revision at **actual server emission**; a degraded commit, frame arrival or heartbeat does not renew those instants. A client consumes pre-data status only with its matching validated epoch+revision data; a missing matching status is protocol failure. TTL = `2×lightSampleMs + 2×snapshotDeadlineMs + 2×jitterMillis` = **11,500 ms** with defaults. Periodic status may carry a newer revision but cannot freshen an older client frame; same-revision status may age/invalidate it. Respect explicit per-section degraded/availability flags and existing coarse process/PSS timestamps; no fictitious precision or extra host work. Timeouts do not cancel blocked syscalls.
- Cost model, **not capacity proof**: with `N` streams and 5 s recheck, ≈`N/5` policy **checks/s** but ≈`2N/5` persisted **DB reads/s** for successful session+user lookups (at 32 ⇒12.8 reads/s), plus admission/WS/REST work. For complete data-event `B` bytes and publication interval `T`, max consumed payload ≈`N×B/T` bytes/s; at 32, 256 KiB, 5 s ≈1.6 MiB/s, excluding controls/retransmission. Latest-only retention reduces superseded application frames, not sent bytes. HTTP/1.1 browser connection limits commonly ~6 per origin; HTTP/2 concurrent streams/flow control are negotiated. One stream per captured owner, preserve normal API headroom and qualify deployed proxy. ([MDN connection warning](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events#warning_when_not_used_over_http2); [RFC 9113 §5.1.2, §6.5.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.1.2))

## Selected bounds (architecture governs)

| Concern | Selected contract / research limit |
|---|---|
| Sampling ownership | One startup-owned monitor; zero subscriber-triggered host reads |
| Browser connection | One bearer Fetch SSE per captured visible/consuming connection owner; REST fallback snapshot 15 s and visible-detail metrics 5 s; no resource polling while hidden |
| Application buffering | One latest `watch` frame, at most one cached frame and no new encoding at zero interest; small per-data status at server emission, no per-client full JSON |
| Heartbeat / proxy idle timeout | 15 s transport-only comment / ≥45 s at every proxy hop; buffering and compression off |
| Admission and origin | Global 32 → validate present Origin → 2 s auth cap → bearer → actor 4; absent Origin permits authenticated CLI, dev still checks present Origin |
| Session recheck | Independent 5 s supervisor, 2 s lookup timeout, two persisted reads on success; cutoff of new emission even when body unpolled, not guaranteed network close |
| Freshness | Age since last successful snapshot/metrics observation + revision-correlated status before each data; TTL formula yields 11.5 s by default; per-section flags still apply |
| Replay | Full current snapshot on connect/reconnect; no event IDs, no `Last-Event-ID` history |

## Unresolved questions

- Which native targets actually expose a cancellable, authenticated owner-bound streaming Fetch? Unsupported targets stay on REST rather than guessing.
- Which reverse proxy/CDN/LB is used in packaged deployments, and what are its idle/read timeouts, buffering, compression, and HTTP/2 settings?
- What is the representative combined snapshot+metrics+alerts data-event size against the selected **256 KiB complete-event cap**? No service/load measurements or credentials were used for this exploratory research.
