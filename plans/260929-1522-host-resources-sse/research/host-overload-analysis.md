# Host-resource SSE: overload and qualification analysis

Date: 2026-09-29. **Exploratory planning research, not the contract or release-capacity proof.** [Authoritative host-resource SSE architecture](../../../docs/architecture/host-resource-sse.md) governs conflicts: in particular, bearer Fetch (not EventSource/cookies), independent auth supervision, `2N/5` persisted DB reads/s rather than `N/5` checks/s, and precise revision-correlated freshness status. Scope is the existing per-server-process monitor and its prospective bounded authenticated SSE reader; preserve WS alerts/history, host actions, collection ownership and cadence. Baselines cite `server/src/system/monitor.rs`, `server/src/system.rs`, `server/src/system/config.rs`, the Linux collector and [local-collector-profile.md](local-collector-profile.md). Earlier [transport research](sse-transport-and-security.md) is exploratory where it differs.

## Ground truth and accounting boundary

- Existing `HostResourceMonitor::new` **synchronously** constructs `HostMetricsSampler` (`System::new_all`, CPU/memory refresh, disk list) and samples once before returning (`monitor.rs:68-112`, `system.rs:39-55,68-128`). This startup may stall on disks; moving delivery to SSE does not eliminate it. One background monitor runs even at zero subscribers; a light tick calls `spawn_blocking` for the deep source, then separately calls legacy `spawn_blocking`, then commits both sections under one cache write lock (`monitor.rs:234-441`). REST snapshot and metrics clone from cache (`monitor.rs:163-178`, `api/system.rs:9-19`); adding a subscriber must not repeat sampling.
- Default **clamped** tuning: light 5 s, processes 15 s, PSS 60 s, jitter 0-250 ms, process *cooperative* deadline 150 ms, deep-source wait deadline 500 ms; bounds respectively 1-60 s, 5-300 s, 15-600 s, jitter ≤1,000 ms, process 10-1,000 ms, source wait 50-2,000 ms (`config.rs:62-84,126-136`). The 500 ms is a wait timeout, **not CPU or blocking-syscall budget**. `docs/system-architecture.md:4774-4778` says 100 ms process deadline; current config/default 150 ms is normative. Documentation needs reconciliation, not a silent behavioral change.
- Process inventory checks the clock between reads, limits scanned PIDs to 4,096, returned processes to 20, PSS (`smaps_rollup`) to top 5 only on PSS ticks, strings to 256 bytes, each bounded text read to 256 KiB (`linux/process.rs:77-175,213-246`, `platform.rs:9-34`). It still iterates/read-stats per PID and sorts scanned records. Cgroup, mount, power, PSI, meminfo and `/proc`/`/sys` reads, filesystem free-space `statvfs`, and the **separate** sysinfo disk-refresh/thermal-zone legacy sampler incur I/O, allocation, and possible blocked remote or unhealthy filesystem latency. The 256 KiB *per-file* read bound is not an SSE frame bound. The process deadline cannot interrupt a current blocking read. Existing `pending_collection` avoids new deep workers while a timed-out worker remains alive, but the monitor still awaits the legacy sample with **no deadline** (`monitor.rs:256-278,297-335,443-460`). A blocked legacy read prevents commits; unpolled/no-sample state must become stale, not healthy. Do not add parallel retry workers or claim this feature fixes the legacy collector.
- Existing cache updates clone snapshots/alerts and carry old process/PSS on skipped cadence; deadline path marks stale and advances `sampled_at`, which is **not** a successful-observation clock. Proposed SSE cache stores independent last-successful deep/legacy `Instant`s with each observed/degraded commit. On changed effective clamped freshness config (`light`, wait deadline or jitter), atomically commit a **metadata-only new revision** with retained snapshot/metrics/alerts and both observation instants; do not sample or emit alerts. Identical effective config creates no revision. Revision-bound TTL avoids old reconnect frames claiming health at a new shorter TTL; status tick/degraded synthetic timestamp never resets observation ages.
- Measured on **one development Linux host** by `bash scripts/profile-host-resource-deep-scan.sh 10 /home/loidinh/WS/dam-hopper`: ten back-to-back **full** process+PSS scans, mean 47.075 ms CPU, peak 48.262 ms CPU, peak 48.568 ms wall, peak 518 PIDs, 0 deadlines, largest serialized *deep snapshot* 7,505 bytes, RSS delta 659,456 bytes. `server/examples/host_resource_profile.rs:68-84` stops CPU/wall clocks **before** JSON encoding. Measurement excludes legacy sysinfo sampler/startup, JSON encoding, SSE framing, auth/database, alerts, socket/proxy and UI; no whole-monitor, whole-host or weak-host proof. [INFERENCE] 47.075 ms every 5 s is ~0.942% of one core for hypothetical all-deep ticks; actual production process/PSS cadence differs. A ten-scan RSS delta cannot establish a leak.

## Proposed incremental cost model (not observed capacity)

Use consistent **CPU seconds per wall-clock second** (one core = 1 s/s). Let `c_light`, `c_process`, `c_pss` be disjoint CPU seconds per corresponding deep-collector stage invocation, `c_legacy` CPU seconds per legacy invocation, and `Tlight`, `Tprocess`, `Tpss` their actual average interval seconds (default nominal 5/15/60, jitter and skipped/blocked work measured, not assumed). Baseline monitor cost is `R_collect ≈ c_light/Tlight + c_process/Tprocess + c_pss/Tpss + c_legacy/Tlight` CPU s/s, **not** one `C_deep` CPU per tick plus a separately counted subset. If stage timings overlap or the measured full-scan `c_full` includes all three, use observed total deep CPU rate instead; **never** insert `c_full` and its component estimates in the same sum. The ten full process+PSS profiler scans measured `c_full` only, not stage shares or a production cadence. At best `[INFERENCE]` 47.075 ms every hypothetical 5 s ≈0.009415 CPU s/s =0.942% of one core for deep collection alone; this is not the actual mixed-cadence/legacy cost.
Let `N` admitted bodies (≤32 process-wide, ≤4 per subject), `B` complete data-event bytes (≤262,144), `Tpub` measured average seconds per **published** distinct revision while interested, `S(B)` **server-process** CPU seconds for one bounded JSON+SSE framing encode, `E(N,B)/Tpub` **server-process** socket/TLS/fanout CPU s/s excluding `S`, `R_control(N)` server CPU s/s for per-client small status/heartbeat, and `R_auth_server(N)` server CPU s/s for independent checks plus admissions. Then `R_server ≈ R_collect + R_other_baseline + 1[N>0]×S(B)/Tpub + E(N,B)/Tpub + R_control(N) + R_auth_server(N)`, with `E(0,B)=R_control(0)=0`. Separately model persisted **read count** `2N/5` reads/s on successful checks, plus admission/WS/REST reads; external DB CPU is `(2N/5)×c_db-read` CPU s/s **at the DB**, not added to server-process CPU or mixed into one-core target. If the DB is colocated, report host-level combined CPU in a separate total without counting its process twice. No `N×S(B)`, `N×R_collect`, duplicate framing, or duplicated auth/egress component. For changing frame sizes sum costs over actual published revisions rather than substitute one `B`; measure server CPU, external DB CPU and proxy CPU separately. At `N=0`, baseline monitor/alerts continue, publisher retains ≤one encoded frame and performs **zero new encoding**; on next interest reuse it if its revision remains current, otherwise single publisher encodes latest pair once. First demand does no OS read; frames capture the same atomic committed pair/revision on successful and degraded updates. Never hold cache/watch locks over encoding, awaits or network.

`R_payload ≈ N × B/Tpub` bytes/s only if every reader consumes every published revision. For measured **snapshot-only** 7,505 B (not a combined frame), `N=32,Tpub=5 s`: 48,032 B/s; `Tpub=1 s`: 240,160 B/s, **both lower bounds for the actual frame**. At the hypothetical full 256 KiB frame cap, `N=32,Tpub=5 s`: 1,677,721.6 B/s ≈1.6 MiB/s; at `Tpub=1 s`: 8,388,608 B/s =8 MiB/s; `N=1,Tpub=5 s`: 52,428.8 B/s. Headers, 15 s status/heartbeat, network retransmission and buffers add cost; jitter and coalesced/skipped revisions change the actual rate. A process max of 32 applies per backend process, not globally across a fleet/load-balanced cluster. Require a bounded writer on the **complete encoded data event**; oversize ⇒ bounded status/error, stop SSE for that generation and REST fallback, no truncation or serialization retry amplification.

Proposed Tokio `watch` holds only the latest shared immutable pre-encoded `Bytes`/`Arc` and allows skipping superseded revisions. **This does not imply O(B) total memory:** each of N slow bodies can retain a distinct older shared in-flight revision. Bound just application frame retention as `O((N+1)×B)`: at 32 and 256 KiB ≈33×256 KiB = **8.25 MiB**, even without per-client deep clones; at 7,505 B ≈247,665 B if frame were only that snapshot. Add cache/snapshot+legacy pair, publisher staging buffer, auth leases/tasks, parser state, Hyper/TLS, OS socket buffers, reverse proxy buffers and browser buffers. `watch` bounds pending application revisions, **not queued network bytes or bytes already sent**. Flow control/one outstanding application event per reader, body-drop cleanup, independent revocation supervisor and shutdown cancellation matter; cannot retract bytes queued after revocation. RSS target measures process RSS; kernel/proxy buffering requires separate measurement/control.

Persisted `AuthService::evaluate_claims` reads session then user and checks revocation, versions, expiry and MFA; 5 s supervisors imply ~`N/5` checks/s, ~`2N/5` successful DB reads/s (32 ⇒12.8), plus admissions/WS/REST. Each check has 2 s cap, independent body-unpolled deadline and no-emit lease; already-queued bytes cannot be recalled. GET order: global 32-slot reservation → explicit present-Origin check → 2 s **authentication helper only** → bearer check → per-subject 4-slot → handler. Factor existing `require_auth` into one reusable auth/policy helper and leave `Next.run` **outside** timeout; slow publisher/serialization is not AUTH_UNAVAILABLE. On timeout drop helper future, return **503 JSON** `{ "code":"AUTH_UNAVAILABLE", "error":"Authentication backend unavailable" }` and release global slot; no double auth check. `AdmissionPermit(Arc<Mutex<Option<OwnedSemaphorePermit>>>)` is Clone-safe in HTTP extensions; unique `take()` transfers permit to body Drop lease, and error/timeout/cloned extension releases at most once. Configured CORS handles preflight without permits or DB; empty allowed-origins omits CorsLayer and GET-only OPTIONS is 405 without permits/DB. Disallowed present Origin rejects before auth including dev mode; absent-Origin CLI still bearer-authenticated. Finite global/subject 429 includes `Retry-After:30`; profile owner retries remain capped and no query tokens/cookie SSE.

Status at most 15 s apart and **immediately before each selected data frame** with no interleaved event: derive paired status from immutable frame's epoch/revision/successful-observation instants and clamped TTL configuration at actual emission, never newer monitor cache. Periodic status reads only metadata via `current_status_basis()` (epoch/revision/instants/TTL inputs); it must not clone full snapshot+metrics for each body. Matching pre-data status is required; newer periodic status never freshens older data. A changed freshness config yields **new metadata-only revision**, same actual observation ages, newly authoritative TTL even with no new sample; unchanged config yields no revision. `snapshotAgeMs`/`metricsAgeMs` null when unobserved; TTL `2 × lightSampleMs + 2 × snapshotDeadlineMs + 2 × jitterMillis`: defaults 11,500 ms; 1 s light gives 3,500 ms. Client continues local monotonic aging; heartbeat and cached data receipt do not reset age, availability/degraded flags still apply. A new fetch attempt may accept an equal prior revision as its initial full baseline only with a **fresh adjacent matching status**; deduplicate within that attempt. No replay or event ID.

## Admission/load matrix: deliberate fixtures, not measured results

Nominal payload at `B=256 KiB` and hypothetical `Tpub=5 s`; reads/s are **incremental persisted** auth reads at steady state only. For mixed actors, distribute under per-actor four-slot cap. `33` means 32 already admitted, then one new request; `actor 5` means four for one subject, then a fifth (even if global slots remain). At `N=0`, baseline monitor CPU still exists.

| Attempted/admitted | Expected behavior / structural assertion | Max modeled payload MiB/s; auth reads/s |
|---|---|---|
| 0 / 0 | monitor and alerts keep ticking; publisher emits/encodes nothing | 0; 0 |
| 1 / 1 | one owner stream, first demand reads cached pair only; same collector count | 0.05; 0.4 |
| 4 / 4 | two fleet/detail observers for one owner still share **one** stream; four distinct owners if testing four | 0.2; 1.6 |
| 16 / 16 | four distinct actors × four streams or ≥16 actor owners; latest-only under slow readers | 0.8; 6.4 |
| 32 / 32 | eight distinct actors × four; measure CPU/RSS/DB/network for release qualification | 1.6; 12.8 |
| 33 / 32 | 33rd receives 429+30 s Retry-After without auth DB if global full; no body/slot leak | 1.6; 12.8 (excluding rejected attempt) |
| actor 5 / 4 | 5th same actor receives 429 even with unused global capacity; no retained zero-count key on close | 0.2; 1.6 (excluding rejected attempt) |

Browser HTTP/1.1 commonly allows ~6 connections per origin; a long-lived SSE uses one, so many profile targets to one origin and existing REST/WS may contend, even before server's cap. HTTP/2 multiplexing is subject to negotiated concurrent-stream/flow-control limits; test deployed proxies as well as loopback direct and preserve normal REST headroom. No change to server-wide HTTP limits is in scope.

## Proposed go/no-go and release qualification

These are **proposed gates, not observed measurements**. Phase-00 reproducible N=0 whole-monitor baseline uses `bash scripts/profile-host-resource-monitor.sh --workspace <isolated-workspace> --warmup-seconds 60 --duration-seconds 300 --output <redacted-report.json>`; same flags and named host/config for comparisons. Wrapper builds before bounded child, enforces warmup+duration+30 s child timeout (TERM then 5 s KILL), emits blocked/nonzero rather than claiming a blocked collector shut down. JSON `schemaVersion:1`, `status`, safe reason, host/config/timing/startup/steady CPU-ms+RSS-bytes and `counts.*:{value:null,reason:"unavailable..."}` where monitor internals do not expose stage counters; never label unavailable counters zero or infer whole-monitor CPU from ten deep scans. Phase 05's opt-in `#[cfg(test)]` SAME-live-process real-monitor+router/auth-actor harness supplies redacted out-of-band JSONL/ready metadata for incremental committed/encoded/auth/permit counts; never production API/telemetry. Record named reference/weak hosts, DB/proxy, load and independent process CPU observer, run N=0/1/4/16/32 and 30 min soak; unavailable mandatory live counters or DB block release, no silent goal lowering.

- **Structural must-pass:** unchanged collection rate/workers for all N including N=0, ≤1 publisher encoding per committed revision with interested readers, zero new encodes and ≤one retained encoded frame at zero interest; reuse unchanged retained frame on renewed interest; ≤256 KiB complete data event or explicit bounded failure; admission ≤32 process and ≤4 subject, global fast reject and explicit present-Origin rejection before auth, no per-client backlog; no stale-source health claim or unauthorized **new emission** (wire/proxy bytes already queued cannot be recalled); old REST cannot overwrite SSE and SSE cannot mutate a superseded owner. Capture latest pair atomically; send status from selected frame's captured successful-observation metadata immediately before its data event, and do not promote periodic newer-revision status into freshness proof for older cached data. A connected socket alone is not proof of freshness.
- **Incremental SSE CPU:** ≤1 percentage point of **one core** at N=1, ≤3 points at N=32, steady state. Serialized complete frame p95 ≤5 ms on the **named reference host**. p95 sample commit→UI ≤1 s on loopback, **excluding sampling/proxy time**. Use both default 5 s and configured 1 s cases; the higher cadence is a stress case, not a permission to increase sampling in normal deployment.
- **Process RSS:** incremental ≤32 MiB at N=32 after warmup; growth ≤1 MiB in the final ten minutes of a 30-minute steady run; after final client disconnect, feature stream tasks/permits/subject map counts back to baseline ≤5 s. Allocator-held RSS need not drop on disconnect. Measure kernel/proxy buffers separately; document if flow control invalidates the workload assumption.
- **Whole monitor** is a separate goal of ≤2% of one core on the reference host at default cadence, not demonstrated by deep-only profiler. If existing baseline misses it, record baseline failure and review alert impacts before any *server-owned existing-cadence* tuning; do not blame SSE, silently weaken targets or rewrite collectors in this transport feature.
- **Fail/no-go** on any security/availability/freshness/structural invariant or unreconciled qualification threshold. If a weak host legitimately cannot meet reference-host CPU targets, report reference result and weak-host behavior separately; do not claim universally bounded host cost. Proxy-specific qualification remains required before rollout.
