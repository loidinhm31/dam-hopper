# Agent Store paths and notifications

## Outcome
Agent Store tabs become **Store / Memory Files / Agent Settings / Import**. Agent Settings owns OMP extension lifecycle plus OMP and Codex notification policy. The configured OMP directory selects status/install/update/uninstall; the configured Codex directory selects config inspection and notification sync. Turning on either master toggle is possible **only after server verification** that the selected install/config directory is the actual notification runtime directory; OMP additionally has a verified managed extension, Codex has an existing valid config. Neither a guessed browser home nor the API service account's home may masquerade as the terminal user's home. Existing alerts from stale enabled settings fail closed until reverified.

## Findings and constraints
- `AgentStorePage.tsx` currently renders `integrations` → `OmpExtensionManager`. That manager passes `undefined` to status/install/uninstall, so all operations use server defaults; `targetPath` is only a display label. `client.ts`, `queries.ts`, `ws-transport.ts` already accept/forward optional `agentDir`; query keys include path/profile generation and mutation invalidates the profile prefix. Keep this route, change caller and verification contract.
- `server/src/api/agent_status.rs` rejects explicit `~` as relative, defaults to `PI_CODING_AGENT_DIR` or `dirs::home_dir()` (API identity), creates the chosen directory on install. `server/src/agent_status/integration.rs` checks the agent dir and managed file; `extensions/`/ancestor symlink and writable-directory safety need review before accepting an arbitrary authenticated path. CLI requires an existing absolute directory (`docs/architecture/agent-status.md`).
- `SettingsAppearanceSection.tsx` embeds `TerminalAgentNotificationSettings`; `stores/settings.ts` persists version-1 per-agent policy to global UI config. `server/src/api/config.rs` writes Codex `config.toml` on master-state change to `dirs::home_dir()/.codex` regardless of any UI-selected Codex directory, and can create it. `terminal-agent-notification-integration.ts` currently checks only `.enabled` at OMP and Codex delivery points. `agent-status-types.ts` has no path eligibility response; its `AgentKind = "omp"` is the *status reporter* protocol and must not be broadened merely to render Codex preferences.
- Linux production API unit defaults to `dam-hopper:dam-hopper` with HOME under its API home (`docs/linux-systemd.md`). PTYs are spawned by the API identity; `pty/manager.rs::build_child_env_from_parent_snapshot` synthesizes HOME from euid if needed and accepts per-session env overrides. A remote browser cannot establish its own `$HOME` on that host; `/home/<user>` is an absolute server path, but POSIX permissions apply. An API run as `dam-hopper` cannot write another user's private home without deliberate provisioning. No implicit privilege elevation.
- `docs/development-rules.md` and workspace `.omp/skills` are absent in this checkout; planning skill loaded from `~/.omp/agent/skills/planning/SKILL.md`. Architecture proposal is recorded under `docs/architecture/agent-status.md` (explicitly marked not yet implemented).

## Chosen contract and security boundary
1. **Persist server-profile-specific path choices**, not browser-local paths, in the selected server's existing global UI config, e.g. `agentSettingsPaths: { ompAgentDir: string, codexDir: string }` (camelCase API / snake_case TOML). Extend `server/src/config/schema.rs`, `packages/ui/src/api/client.ts`, `packages/ui/src/lib/ui-config.ts` and setting hydration. Defaults derive from **server-reported effective PTY HOME**, not from JavaScript `~`. Existing installs/configs are not moved; unresolved old path settings remain disabled until inspected. Store path edits separately from the master enable action; an edit invalidates eligibility immediately and never silently retargets a previously enabled policy.
2. Add a narrowly scoped authenticated server inspection endpoint (proposed `GET /api/agent-status/paths?agentDir=...&codexDir=...`) returning `serverHome` (effective PTY HOME), normalized absolute `ompInstallDir`, `ompNotificationDir`, `codexConfigDir`, `codexNotificationDir`, status (`current | outdated | absent | modified` for OMP), Codex config validity, and per-agent `canEnable` + specific block reason. Choose concrete DTO fields once and mirror in `agent-status-types.ts`. An input path is **not** proof of its own notification path: derive OMP effective runtime path from PTY HOME and `PI_CODING_AGENT_DIR`, Codex effective config dir from PTY HOME/`CODEX_HOME` and the config-sync target. If a PTY/session can override any of these unpredictably, surface an unverified/mismatch result and block enablement for that terminal until actual effective environment can be established. Do not claim global verification when mixed active terminal environments disagree.
3. Resolve exactly leading `~/` relative to **server's effective PTY user's home** (or disallow with explicit resolved-path help if this cannot be established); accept absolute paths. Reject bare `~`, other-user `~name`, empty explicit values, relative paths, `..` traversal, non-directory paths, symlinked target/parents and path escapes per existing managed-extension rules. Use the same normalized canonical directory identities for comparison, status, install, uninstall, notification delivery and Codex sync. Return the resolved directory and actionable error, not an unverified server-home fallback. For absolute `/home/loidinh/.omp/agent`, retain that path; enforce filesystem permissions under the API euid rather than rewriting to `/var/lib/dam-hopper`.
4. Backend policy gate: `update_global_ui_at_path_with_codex_home` / `merge_global_ui_config` must reject transition to enabled (including path changes while enabled) if fresh verification fails; allow disabling and other settings edits even if path is missing. Revalidate persisted enabled policies at delivery time, not just when saving: stale/offline/unknown/mismatched state produces no OMP or Codex toast/history/sound/browser alert, and must not suppress status badges. Align Codex config sync with the verified configured directory (not `dirs::home_dir()`); never create a different `~/.codex`, and require existing readable, regular, parseable `config.toml` before turning on. Preserve unrelated TOML keys; disable remains possible if config disappears. Avoid blocking websocket rendering on filesystem I/O: refresh bounded eligibility on path/config/install changes and reconnect with fail-closed invalidation; delivery reads validated per-profile state. Installation/uninstallation invalidates eligibility immediately. Keep the existing policy version and channel options unless schema migration is needed for path fields.
5. Filesystem/production: use existing authenticated API and managed extension hash checks; no arbitrary shell command, `sudo`, generic helper, chmod/chown or symlink-following writes. Check ownership/write permission before mutating; return explicit permission-denied (including `dam-hopper` service euid and target, without sensitive file contents). Deployment supports either an API running under the same OS identity as target OMP/Codex sessions or administrator-provisioned, **narrow** traverse/write ACLs on only required directories. Document safe one-time provisioning, rollback and the fact that service PTYs must actually execute with the matching HOME; do not recommend making all of `/home/<user>` writable. If policy disallows such access, report the missing OS permission rather than advertising a working browser install. Do not weaken existing CLI verification.

### Eligibility truth table
| State | OMP master on allowed? | Codex master on allowed? | Existing enabled preferences |
|---|---|---|---|
| Exact normalized runtime/selected path, managed OMP **current**, Codex existing valid config | Yes | Yes | Deliver for verified agent/profile |
| Exact path, OMP absent/outdated/modified or unreadable | No | Independent Codex check | OMP delivery blocked; offer install/update if safe |
| Exact path, Codex config missing/malformed/unreadable or sync unwritable | Independent OMP check | No | Codex delivery blocked; allow off |
| Paths differ, changed but unverified, API disconnected, unknown PTY env, or permission error | No | No | No delivery for affected agent/profile; warning explains cause |

**Design caveat:** OMP `outdated` is managed but cannot be claimed as verified *current* for this release; user must update. If a user sets a custom OMP path or Codex `CODEX_HOME`, match it to the actual process environment before enabling rather than assuming the default profile. Explicitly handle mixed PTY environments as separate verified terminal gates or fail closed for mixed profile; do not replace this check with comparing two UI fields copied from one input.

## Dependencies, trade-offs and risks
- Phase 1 defines backend verification truth; Phase 2 consumes it; Phase 3 depends on typed response; Phase 4 closes dispatch-time bypass. Build backend and client types against one agreed JSON contract before UI polish.
- Server-relative `~` with a documented, checked PTY home is safer than trying to discover a remote viewer's home. An absolute input is simpler when PTY effective home cannot be guaranteed. A broad privileged installer is rejected: extra service and escalation surface for a single managed file. Same-user or minimal ACL provisioning is the only declared production access strategy.
- Beware global UI config vs currently selected profile: optimistic writes and cached verification must be owner/generation-fenced. Browser permission is separate from filesystem eligibility; enabling browser popup must not imply installer eligibility. Config file or extension may be removed externally at any time: fail-closed invalidation and bounded re-check, never a permanent trust cache. Atomic Codex writes must not clobber unmanaged fields or leave policy enabled after failure.
- Do not delete `TerminalAgentNotificationSettings` molecule if useful in unified organism; remove only old mounting point, obsolete manager and stale references/tests. No source-implementation snapshots or tautological status assertions.

## Unresolved questions
None blocking implementation. The release operator must choose same-user API deployment or restricted ACL provisioning for a specific home; the server must report unsupported permissions rather than silently selecting another target.
