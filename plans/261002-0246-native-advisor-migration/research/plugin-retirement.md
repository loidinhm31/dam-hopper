# Dam-Hopper plugin-platform retirement inventory

Research date: 2026-10-02. Scope expanded by main-agent decision to retire the full Dam-Hopper plugin platform, not only Advisor. Planning research only; no application/config changes or service actions.

## Executive findings

- Only concrete runner service found in either repository is the system unit `dam-hopper-plugin-runner.service` (`deploy/systemd/dam-hopper-plugin-runner.service.in`, `server/src/linux_release/constants.rs::RUNNER_SERVICE_UNIT`). No Evcrate user-level Advisor unit is referenced by searched source/scripts/workflows. A live user-scope query was unavailable because this environment has no user DBus/XDG runtime.
- Read-only systemd inspection found the unit **loaded, active, running** at `/etc/systemd/system/dam-hopper-plugin-runner.service`, `MainPID=3971358`, `User=dam-hopper-plugin-runner`, `Group=dam-hopper-plugins`. Do not treat rollout as an empty-host cleanup.
- Preserve server HOME history: `deploy/systemd/dam-hopper-api.service` sets `HOME=/var/lib/dam-hopper`; Evcrate producer writes `~/.evcrate/advisor-history` (`.evcrate/source/.evcrate/bin/lib/advisor/history-store.cjs::historyContext`, `tests/advisor-controller/history-controller-integration.test.cjs`). Do not remove history, API HOME, or generic `/run/dam-hopper` contents as plugin cleanup.

## Dam-Hopper removal map

- Remove plugin engine `server/src/plugins/**`, runner binary `server/src/bin/dam-hopper-plugin-runner.rs`, plugin test server `server/src/bin/dam-hopper-plugin-test-server.rs`, and `pub mod plugins` from `server/src/lib.rs`.
- Remove `AppState::plugin_service` construction/access (`server/src/state.rs`); plugin API modules/routes (`server/src/api/plugins.rs`, `plugin_admin.rs`, `plugin_assets.rs`, `api/router.rs`); plugin-only auth gate `require_plugin_admin` and logout's `plugin_service.revoke_actor` call (`api/auth.rs`). Keep ordinary authentication, admin authorization, session revocation and other API routes.
- Remove plugin WebSocket epoch issue/revoke (`server/src/api/ws.rs`) and only `PluginGetEpoch`, `PluginEpoch`, `PluginRevoked` protocol variants (`server/src/api/ws_protocol.rs`). Preserve WebSocket auth, sessions, MFA, terminal and general connection lifecycle.
- Remove plugin SDK `packages/plugin-sdk/**`, UI bridge/runtime `packages/ui/src/plugins/**`, `packages/ui/scripts/plugin-test-client.mjs`, `PluginHost.tsx`, `PluginFrame.tsx`, `PluginUnavailableState.tsx`, and `packages/ui/src/api/plugin-types.ts`/plugin-specific API client methods.
- Remove settings registration/grant/binding UI and tests: `packages/ui/src/components/pages/settings-page/PluginManagementSection.{tsx,test.tsx}`, `PluginAccessModal.tsx`; remove its `SettingsPage.tsx` mount/mock. `packages/ui/src/components/organisms/WorkspaceAdvisorHost.tsx` is currently a plugin host: replace its runtime with native Advisor, not a plugin compatibility shim. Keep/reuse `WorkspaceAdvisorContext`, `AdvisorPanelSlot`, slot placement/geometry, and `WorkspacePage.tsx` composition where needed for native surfaces.
- `computeSha256Hex` is exported through `PluginAccessModal`/`PluginManagementSection`; preserve/rehome it as an OPTIONAL path-hash utility. It must not gate access or history discovery. `packages/browser-bridge` is also used by `apps/native/src-tauri/build.rs`; do not remove it as plugin debris.

### Deployment, runner ownership, and runtime paths

- Remove runner owner CLI/config throughout `deploy/release/dam-hopper-install.sh`, `server/src/linux_release/cli.rs`, `host_config.rs`, `stage.rs`, `stage_units.rs`, `account.rs`, unit render/policy, activation/rollback/recovery/status, and `api_runtime.rs`: `--plugin-owner-user`, `plugin_owner_user`, `@ADVISOR_OWNER_*@`, `@PLUGIN_SHARED_GROUP@`, plugin group/user provisioning, runner health/startup checks.
- Remove runner system unit, runner tmpfiles template, runner binary, registry/runtime and `dam-hopper-plugins` shared-group integration. Fixed paths/contracts: `/run/dam-hopper/plugin-runner.sock`; `/etc/dam-hopper/systemd` is **not** the unit dir (actual systemd FragmentPath is `/etc/systemd/system/dam-hopper-plugin-runner.service`); plugin tmpfiles is `/etc/dam-hopper/tmpfiles.d/dam-hopper-plugin-runner.conf`; `StateDirectory=dam-hopper-plugin-runner` gives `/var/lib/dam-hopper-plugin-runner`, registry at `<state-dir>/plugins`. Runner unit runs configurable non-root owner; default account/home is `dam-hopper-plugin-runner` / `/var/lib/dam-hopper-plugin-runner`, primary group `dam-hopper-plugins` (`account.rs`, `unit.rs`, runner unit template). Never delete a custom owner account/home.
- Do **not** simply delete tmpfiles: both API and idle-suspend helper templates currently depend on its `/run/dam-hopper` directory, with API/helper supplemental plugin group. Replace this with a non-plugin runtime tmpfiles contract and API/helper group/permissions that still support `server.pid` and `/run/dam-hopper/idle-suspend.sock`; retain API/helper/recovery/systemd socket units and helper audit data (`deploy/systemd/dam-hopper-api.service.in`, `dam-hopper-idle-suspend-helper.service.in`, `.socket.in`). `deploy/reset-linux-production.sh` is idle-suspend cleanup, not a plugin uninstaller.
- `runtime_cleanup.rs::cleanup_stopped_plugin_runtime` validates all managed producers are stopped and removes `plugin-runner.sock`, `idle-suspend.sock`, and `server.pid` with no-follow/type/inode checks. Refactor/rename this shared cleanup; retain safe idle-suspend/PID cleanup for release transactions, but a plugin-only manual cleanup must never unlink helper socket or PID while the server/helper is live.

## Persisted state and compatibility (do not cut over by deleting fields)

- Manager state lives at `/var/lib/dam-hopper-manager/state.json`; current `MANAGER_STATE_SCHEMA_VERSION=2`, legacy `1` (`constants.rs`, `state.rs::load_or_init_manager_state`). `ReleaseRecord` and `PendingCandidateRecord` are `deny_unknown_fields` and persist runner unit/tmpfiles hashes, owner UID/name, admin-config digest, Node version/digest and plugin-enabled state (`state_record.rs`). Removing fields directly makes existing state fail to deserialize. Plan a strict legacy reader/one-time atomic canonicalization preserving active/previous/pending/transaction/generation and non-plugin hashes; decide explicit schema version and n-1/rollback compatibility before writing the new shape.
- `/etc/dam-hopper/host.toml` `HostConfig` is also `deny_unknown_fields` and persists `plugin_owner_user` (`host_config.rs`). Add narrow legacy parsing/removal of this key while preserving role, origins and `service_user`; do not make all host config permissive. Audit `api/agent_status.rs` home lookup, which currently falls back from `service_user` to `plugin_owner_user`.
- Release manifest schema is separate from manager-state schema: release manifest current/legacy constants are 2/1 (`linux_release/constants.rs`); JSON schema allows 2/3 and runner component/service are optional. New manifests should omit runner, while installed old manifests may contain it. Preserve explicit old-manifest read compatibility or a legacy DTO; `deny_unknown_fields` means simply deleting `RunnerServiceContract` breaks old installed manifests/rollback. Retain generic release/rollback fields and never declare n-1 compatibility without testing the mixed old/new state and unit transition.
- Remove runner from `ALL_SERVICE_UNITS`, activation, rollback, recovery and status only with an explicit one-time retirement of the old unit. Current `activate.rs`/`rollback.rs` stop/start/provision runner based on unit-file existence; simply deleting the template leaves an already-installed `/etc/systemd/system/dam-hopper-plugin-runner.service` active and may let old release rollback restart it.

## Safe staged/manual cleanup requirements

1. Gate on native Advisor admin toggle, history discovery/read-only behavior, and parity acceptance; retain old release rollback until the migration's rollback boundary is explicit.
2. Provide an idempotent root-only dry-run-first retirement operation. Inspect `systemctl show`/`FragmentPath`/`User`/`Group`; stop and disable only `dam-hopper-plugin-runner.service`, verify inactive/MainPID 0, then daemon-reload and remove only the exact manager-owned unit and plugin tmpfiles file. Do not stop API/helper as a side effect or delete a caller-supplied account/home.
3. Remove `/run/dam-hopper/plugin-runner.sock` only after proving it is a stale socket (not symlink/regular file and not bound); preserve `server.pid`, `idle-suspend.sock`, whole runtime directory and idle-suspend audit/socket units. Refactor manager's existing no-follow cleanup instead of `rm -rf /run/dam-hopper`.
4. Remove only confirmed plugin registry/packages under `/var/lib/dam-hopper-plugin-runner/plugins`; retain API home `/var/lib/dam-hopper` and all `~/.evcrate/advisor-history`. Do not delete old `/opt/dam-hopper/releases/*` wholesale: honor manager active/previous/pending references and rollback retention; purge old runner/Node binaries only after that release is outside rollback eligibility. Remove default user/group only after confirming they are the dedicated manager-created identities and no remaining unit/group references; never remove a custom owner.
5. Keep this a planned admin runbook/script, not an automatic installer side effect; no service was stopped and no live user scope could be inspected in this environment.
