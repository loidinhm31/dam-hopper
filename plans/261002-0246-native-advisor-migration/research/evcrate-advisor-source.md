# Evcrate Advisor source inventory

**Research date:** 2026-10-02  
**Scope:** Evcrate plugin, imported viewer/domain sources, core history producer; checked Dam-Hopper host source only where needed to verify descriptor delivery. Research only: no code/config changes or runtime checks. Native cutover decision: per-server admin toggle; retire the plugin platform.

## Findings

- The plugin is a host/packaging platform around an existing React viewer. `plugin/ui/plugin-main.tsx` mounts `viewer/src/app.tsx` with `DamHopperPortProvider`; it is not the UI/domain implementation.
- Exposed Advisor data API has eight operations, all read-oriented. `history.refresh` scans input and updates only a bounded in-memory plugin snapshot. No exposed operation writes Advisor history, mutates policy, or deletes source data.
- Core Evcrate writes remain outside `plugin/`: `.evcrate/source/.evcrate/bin/lib/advisor/{controller.cjs,history-store.cjs,task-state.cjs}` produce durable V1 history records under `$HOME/.evcrate/advisor-history`. Preserve these and the V1/V2 Advisor domain contracts.
- Native ownership boundary is the whole plugin platform: no manifest/registration/grant/binding/worker/SDK transport/opaque-srcdoc dependency. Port read behavior and required DTO/domain semantics into Dam-Hopper-owned contracts behind one per-server admin toggle. Never reuse `@dam-hopper/plugin-sdk` wire DTOs as the native API contract.

## V1/V2 records and core producer

- Durable protocol remains `evcrate-advisor-history` V1: `src/protocol/advisor-contract-runtime.ts` and `.evcrate/source/.evcrate/bin/lib/advisor/contracts-v2.cjs`. `execution.json` includes V1 `schema_version`, SHA-256 `project_id`, UUID task/consultation IDs, V2 checkpoint + digest, route/receipt/attempts/status/result/error/timestamps. Optional `outcome.json` is V1 with disposition, evidence revision, changed paths, validation, outcome and record time.
- On disk: `$HOME/.evcrate/advisor-history/<project_id>/<task_run_id>/<consultation_id>/{execution.json,outcome.json}`. Core `history-store.cjs:51-75,241-359` computes project ID as SHA-256 of canonical current project root and uses IDs as directory names. It does not store the absolute project path in record identity. `project-metadata.json` stores sanitized display name keyed by project hash; metadata failure does not block a record.
- Core writer: `controller.cjs` calls `recordStartedExecution`, `updateStartedAttempts`, `recordTerminalExecution`; `task-state.cjs` calls `recordOutcome`. `history-store.cjs` applies process lock/recovery, no-follow/pinned directory/file checks, quota, exclusive initial writes, temp+rename/CAS-like replacement and fsync. Terminal update requires an existing matching `started` record; outcome requires matching `ADVICE_READY`; repeated compatible outcomes are idempotent, conflicting outcome is audit-degraded.
- `history-prune.cjs` is a separate core mutation, not a plugin capability. It is scoped to current project; respects `history.retention_days`/`max_bytes` (defaults 30 days/100 MiB), protects `started` records, prunes oldest terminal records, and defaults to dry-run unless explicitly disabled. Keep it/core write semantics distinct from viewer refresh/detail.
- Plugin scanner imports V1 history validators + V2 checkpoint digest + generated `normalizeHistoryRecord`; it validates/pairs execution/outcome IDs, reports missing/invalid outcomes, and computes V2 checkpoint digest where present. Therefore current producer records are compatible with view refresh; there is no separate V2 history-file layout.
- Plugin data API v2 adds root inventory (max 500 items) and `project_id` query; V1 queries have task ID + filters only. In project context, source remains bound to one project. Core project ID is durable/privacy-related identity; plugin `history_identity` is a different SHA-256 binding token, not a requirement for native reads.

## Plugin-only platform and preserve/remove boundary

- Platform files: `plugin/manifest.json`, `plugin/inventory.json`, `plugin/package.json` (depends on vendored `@dam-hopper/plugin-sdk`), `plugin/backend/worker.cjs`, `dispatcher.cjs`, `context-table.cjs`, `request-table.cjs`, `binding.cjs`, `authorized-backend.cjs`, `error-mapping.cjs`, and opaque-srcdoc build (`plugin/ui/vite.config.ts`). Worker hello/context lifecycle/cancel/health/shutdown and provider bridge are not domain operations.
- Adapter/read infrastructure: `plugin/backend/{provider.cjs,data-api.cjs,history-provider.cjs,history-scanner.cjs,history-detail.cjs,snapshot-store.cjs,cursor-manager.cjs,policy-provider.cjs,evaluation-provider.cjs}`. `RefreshQueue` is fair FIFO, one active scan, max queue 32; snapshot cache is per context, max 2/context, 128 MiB worker aggregate, 5-minute idle TTL/LRU. Signed cursors bind snapshot/query; this cache and per-context binding are plugin machinery, not source history.
- Binding `computeHistoryIdentity(normalizedPath)` (`binding.cjs:51-53,162-169`) is unsalted SHA-256 UTF-8 of normalized absolute history-root path, used only for plugin context binding. `context-table.cjs:22-46` may compare it during `/home/*` fallback; neither is access control required by core history. Keep optional hash utility only if useful; never require root registration/hash for native HOME discovery.
- Core history `export`, `prune`, `list`, `show`, `metrics` are in `history-contract.cjs`; they are not exposed plugin operations. Preserve core writer and core prune policy; retire plugin registration/grants/bindings/manifest/SDK worker/bridge as one clean cutover, not only Advisor access UI.
