# Selection Persistence Research

**Conducted:** 2026-10-01. Repository-only investigation; no checks run.

> Final decisions in [design-contract.md](../design-contract.md). User explicitly requires every selected history branch pinned, including active branch; follow-active default/explicit opt-in only. Parent confirmed BranchInfo lacks canonical refs (derive name + isRemote); endpoint edits preserve logical intent pending fresh discovery; confirmed profile deletion clears root/branch preferences but retains unavailable bulk-selection keys.

## Findings and recommendation

- Workspace selection is already persisted as the owner-qualified tuple `ProjectRef | null` in Zustand store `useWorkspaceStore` (`packages/ui/src/stores/workspace.ts:5-8,15-16,51-67`), key `dam-hopper:workspace-state`, version 1. `setSelectedProject` equality compares both `profileId` and `project` (`:20-34`). Reuse it as the sole shared Workspace/Git-page focused project; do not add another selected-project alias.
- Workspace hydration only partializes `selectedProject`; its rehydrate callback syncs the compatibility `activeProject` and removes the legacy unowned key (`workspace.ts:54-67`). No explicit migrate/merge/schema validation is present there. `explorer-tree.ts:9-15,19-30,124-127` is the closest target-keyed persistence pattern: scope by profile + project + `projectTargetCacheKey`, then persist `openMapByTarget`; no custom migration is shown. Validate new persisted records rather than trusting `localStorage`, and version/migrate any changed envelope.
- `useProjectTargetStore` is currently in-memory (no Zustand `persist`; `project-target.ts:36-56,132-227`). Its helpers distinguish owner scope (`projectScopeKey`, uses `projectKey` for `ProjectRef`; `:24-34`), root (`ROOT_TARGET_KEY = "root"`; `:12`), and normalized worktree path (`worktreeTargetKey`; `:58-69`). `useProjectTarget` reads profile-qualified target first, then has a project-name compatibility fallback (`hooks/use-project-target.ts:14-22`). New history preferences MUST use only qualified refs; never copy that fallback into persistence.
- Target snapshots expose `targetKey`, `isRoot`, `available`, and optional `worktree` (`project-target.ts:14-22,85-130`). A worktree is selectable only when `isAvailable && !isPrunable` (`:68-70`); `markProjectTargetUnavailable` and the unavailable maps preserve orphan reconciliation (`:36-56,229-239`). These are target availability semantics, not history-branch persistence, and target choice itself is not reload-persistent today.
- Profile-owned state cleanup precedent: `WorkbenchSelectionsState.handleProfileRemoved(profileId)` and its `subscribeToProfileChanges` listener (`stores/workbench-selections.ts:35-52,125-137`). The profile event API distinguishes `profileListChanged`, `dataChanged`, and `deleted` (`api/server-config.ts:27-37`); profile-list writes choose list-change vs data-change (`:736-746`), deletion emits `deleted` (`:896-903`). Clear only the deleted profile's new state on confirmed deletion. A stable-ID endpoint edit is `dataChanged`, not evidence that persisted UI intent is invalid; keep intent pending reconnection, then reconcile only against authoritative server data. Removed profile connections are tombstoned and cannot reconnect (`api/connections.ts:745-773`).
- `useAggregatedProjects` subscribes to profile and connection changes, issues owner-scoped project queries, and returns `groups`, `allProjects`, `isLoading` (`hooks/use-aggregated-projects.ts:42-69,93-163`). `ProjectSwitcher` treats a selected project missing from `allProjects` as unavailable for display, but does not clear the stored tuple (`components/molecules/ProjectSwitcher.tsx:20-41`). Preserve the tuple on empty results while loading/offline; absence alone is not proof of deletion.
- Existing tests cover owner-qualified workspace selection (`phase-02-unified-shell.test.tsx:136-163`), project target isolation across profiles and unavailable worktrees (`phase-03-files-editor-search-git.test.ts:152-178`; `queries-target-recovery.test.ts:35-51`; `ProjectWorktreesSection.test.tsx:150-182,273-298`), and Git-page initialization/routing from Workspace selection (`pages/GitPage.test.tsx:148-192`). No persisted Git history-branch or Git-page bulk-selection contract was found.

## Minimal proposed contract

- Put cross-page history intent in one small versioned Zustand-persisted store (new `stores/git-history-selections.ts`, or an existing Git-specific store if discovered during implementation), not component state. Key each record by `projectKey(ProjectRef)` + normalized target identity from `normalizeProjectTarget`/`projectTargetCacheKey`; within it keep the last selected VCS-root identity per target and branch intent per root. Use the API's stable root identity (normalized root path only if no stable ID exists).
- Minimal branch intent: `{ mode: "follow-active" } | { mode: "pinned", name: string, isRemote: boolean }`. Store the discriminator even if `name` looks canonical: local `origin/main` can collide with remote `origin/main` (parent observed `GitBranchControl` currently selects by `Branch.name`). Prefer canonical ref when the API supplies it, retaining `isRemote`/name only as needed for rendering. This is view-only; selecting a history branch MUST NOT checkout or mutate the repository.
- `follow-active` is the conservative default and follows the checked-out branch for that target/root. A pin remains independent of checkout. Persist the current root per owner-qualified target, so selecting a nested VCS root restores that root's own branch intent when returning to it.
- Git-page bulk selection needs a separate persisted field, keyed by `projectKey`, with tri-state semantics: `null` = never explicitly chosen/use current empty-means-all default; `[]` = explicit all/empty selection; nonempty = explicit selected project keys. Serialize a sorted/deduplicated array, validate each key, and keep Workspace `selectedProject` untouched on multi-select and Clear. Do not persist an empty Set in a way that collapses uninitialized and explicit-all.
- Use `projectKey`, `normalizeProjectTarget`, `projectTargetCacheKey`, and `normalizeProjectTargetPath` (`api/ownership.ts`, `api/client.ts`, `lib/project-target-path.ts` via current imports) rather than a new key convention/dependency. Validate version, object/array shape, discriminants, and qualified owner key during hydrate/migrate; drop malformed entries individually, not the whole valid map. Avoid writing unowned project-name entries.

## Reconciliation, races, and tests

- **Loading/offline/error:** do not clear a pinned branch, selected root, selected project, or worktree-scoped preference for missing/empty data while query is pending, connection unavailable, or request failed. Keep persisted value dormant; render loading/offline/error distinctly from “no history branches.” `isLoading` plus connection status/query error is more authoritative than `allProjects.length === 0`.
- **Authoritative success:** only after successful current-owner/current-target branch/root/worktree discovery may reconcile. If a pinned local/remote branch is absent, clear just that pin and return that root to `follow-active`; if a root is absent, discard its root-specific entry and choose the API's current/default root. Do not infer deletion from stale cached data or a response for the previous selection.
- **Deleted worktree/root:** on successful discovery that marks a worktree unavailable/prunable or removes it, do not apply its stored branch intent to project root/another worktree. Retain its keyed preference dormant for possible recovery unless product policy explicitly chooses deletion; current target store records unavailable targets. A successfully removed VCS root can be pruned from that target's map. Confirm root identity stability across refresh before pruning.
- **Race fence:** async reconciliation must compare request/query identity (profile + project + target/worktree + VCS root) with current selection before writes; owner switch, worktree switch, root switch, profile removal, or newer request invalidates old results. Guard persisted writes against stale completion as well as stale React rendering.
- Add scoped tests: persist/hydrate owner separation and migration/invalid records; same project name on two profiles; same worktree path on two profiles; root-specific restore; follow-active update vs pinned stable branch; same-name local/remote pin distinction; pin/root/worktree deletion only after authoritative success; stale response after owner/target change; offline/empty results retain intent; Git-page multi/clear reload behavior preserves Workspace selection and the empty-means-all distinction. Extend `GitPage.test.tsx` and add focused store tests; keep existing target recovery tests intact.

## Unresolved questions

1. Does the branch API expose canonical ref names and a stable VCS-root ID, or only `{name, isRemote}` and root paths? Use the strongest existing identity; do not invent one.
2. On confirmed profile endpoint replacement with the same stable `profileId`, should history intent remain dormant for that logical profile or be cleared? Current event is `dataChanged`; current Workspace selection is keyed by profile ID.
3. On confirmed worktree deletion, should its keyed preference be retained for later recreation at the same path or pruned? Conservative default above retains it, but a recreated worktree at that path may be a different identity.
