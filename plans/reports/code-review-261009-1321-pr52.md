## Findings

### P1 — Remove render-time clock sampling from the roster

Location: `packages/ui/src/components/organisms/TraditionalTerminalProjectsDisplay.tsx:177–186`, especially line 184.

The new `useMemo` callback calls `Date.now()` during render. Existing `react-hooks/purity` rejects it. PR Quality Gate job [113695312313](https://github.com/loidinhm31/dam-hopper/actions/runs/37892174280/job/113695312313) failed at this exact line, with `179 problems (1 error, 178 warnings)` and exit 1. Subsequent typecheck/frontend-build steps in this job never run. This is an introduced merge blocker, not an inferred warning.

Recommendation: keep presentation pure. Prefer the existing server-authoritative expiry path; if a client clock remains necessary, supply an explicitly managed, correctly synchronized time input. Do not suppress the lint rule.

### P2 — Do not expire remote observations using the browser wall clock

Location: `packages/ui/src/lib/traditional-terminal-agents.ts:79–81`; caller `TraditionalTerminalProjectsDisplay.tsx:184`.

Server evidence expiry uses server `SystemTime` (`server/src/pty/session.rs:420–424`) and adds the lease to the server observation timestamp (`server/src/agent_status/reducer.rs:814–820`). The new presentation compares this absolute timestamp with local browser `Date.now()`, with no profile-specific time offset.

Reproduction: ready Claude `blocked/approval` observation; server clock 30 seconds behind browser; expiry 15 seconds after server observation. Actual display immediately renders **Unknown**, suppressing Approval; existing terminal badge simultaneously renders **Needs attention**. Fresh renewed observations suffer the same mismatch.

Observed in Chromium using the real display, status store, builder, and terminal badge. Controlled status fixture, not live Claude ingress. Captured screenshot: `/tmp/omp-sshots-159f231de9ac6c96.webp`.

Recommendation: retain authoritative server state/lease updates, or establish a profile-specific server-time basis. A local timer alone cannot fix clock skew. Server already emits Unknown on lease expiry and the client consumes those updates.

### P2 — Initialize Memory Files after a new owner's projects arrive

Location: `packages/ui/src/components/pages/AgentStorePage.tsx:161–166` (new keyed remount), `:194` (loading defaults to empty projects), `:303–304` (ungated editor mount).

The connection-keyed remount immediately recreates `MemoryEditor` while a cold owner's projects query is loading. `MemoryEditor.tsx:20` initializes its project state to `""` and never reconciles it when projects arrive. The native selector then displays the sole available project, but memory reads remain disabled and Save targets the empty project name.

Chromium reproduction with actual `AgentStorePage`, `MemoryEditor`, QueryClient, connected A/B profiles, and recording API transport:
1. A has cached project `only-project`; its memory read loads successfully.
2. Switch Profile to B while delaying B's `projects:list` response. Editor shows `No projects in workspace`.
3. Release the one-project response. Selector displays `only-project`; textarea stays empty; no B `agent-memory:get` occurs.
4. Type a draft and Save. B receives `agent-memory:update` with `{projectName: "", agent: "claude", content: "# New draft"}`.

Controlled transport; no claim of backend persistence. Screenshot: `/tmp/omp-sshots-159f236a6a0db9f8.webp`.

Previously profile changes reused the mounted editor. The new remount introduces this regression for profile switches and generation replacement, even where both workspaces share the same project name.

Recommendation: preserve owner/generation retirement, but defer editor mounting until projects resolve, or reconcile its project selection on hydration. Do not remove owner fencing.
