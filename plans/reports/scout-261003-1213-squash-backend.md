# Backend Scout — Consecutive-Commit Squash

**Scope:** read-only discovery of backend rewrite/ref safety, API ownership, publication, tests, and docs. No runtime checks run; no source files changed.

## Findings

### Rewrite reuse and topology
- `server/src/git/commit_message_rewrite.rs::{get_commit_message,edit_commit_message,snapshot_branch,collect_parent_first,plan_rewrite,rewrite_bytes,publish_checked_ref}` is the strongest existing base: raw ODB objects, parent-first DAG walk, metadata parser/cross-check, typed blocking, signature/mergetag handling, and final ref CAS. `server/src/git/mod.rs` exports the engine and Git DTOs.
- `edit_commit_message` accepts a reachable target anywhere from root through HEAD, including already-pushed commits. `plan_rewrite` includes the target and every reachable descendant, including merge-side descendants; it rewrites descendants parent-first while preserving each tree, ordered parent list, unchanged message, and unrelated raw headers. Existing tests cover root, older non-HEAD target, merge and octopus descendants, and a side-parent target (`server/src/git/tests.rs`).
- This is **not** a drop-in squash implementation: current serialization preserves each node's tree and number/order of parents; squash must create a new commit with the last selected commit's tree and the oldest selected commit's predecessor as parent, then map all descendants. Root-inclusive squash needs a new root object with the final selected tree. Verify the rewritten tip tree equals the captured tree, as `edit_commit_message` already does.
- `plan_rewrite` proves rewrite closure for identity-preserving OID changes, not topology-changing squash. Existing merge tests prove message rewrites can preserve merges; they do not prove a flattened range plus descendant merge remains semantically safe. Conservative option: require an exactly contiguous first-parent range, reject selected merge commits and any merge among rewritten descendants. Broader support needs an explicit parent-mapping/topology algorithm and tests first. Do not treat current merge support as squash safety.

### Ref safety, recovery, and concurrency
- Snapshot must be `{expectedBranch, expectedHeadOid}` from one observation. `edit_commit_message` validates syntax, captures symbolic `HEAD` and branch under git2 transaction locks, then rejects stale branch/tip **before target lookup**. It also blocks active merge/rebase/cherry-pick, a branch checked out in another linked worktree, replace refs, grafts, shallow history, malformed/missing graph objects, and detached/unborn HEAD.
- Snapshot locks are released during the ODB rewrite. Final `publish_checked_ref` locks both `HEAD` and the full `refs/heads/...` ref, rechecks symbolic HEAD and old tip, then commits one branch-ref change via git2 transaction. Competing writer/branch switch fails stale; no app-wide lock spans rewrite.
- Objects are written before ref publication. A failed/stale final CAS leaves unreachable ODB objects; no ref rollback/backup branch/recovery journal is used. A transaction commit error returns `PublicationUncertain` with observed HEAD/ref; it is not automatically rolled back. Active Git operation results may carry `GitRecoveryState` from `cli_fallback::active_git_operation`; rewrite itself creates no rebase/conflict recovery state. Reuse these fail-closed semantics rather than worktree rebase/reset.
- Rewrite touches only the current attached local branch ref. Other refs/remotes/tags are not moved. The API GET for commit message and POST rewrite both operate against the selected worktree's current branch; viewing another log ref does not make it an eligible rewrite target (the shared history docs explicitly disable rewrite actions off the active branch).

### Published history and explicit publication
- `GET /api/git/{project}/log`'s `GitLogEntry.isPushed` comes from the local upstream/tracking OID graph check in `repository::get_log`; it is not a live remote lease. Message rewriting intentionally does not block on it: API docs and `edit_commit_message_allows_dirty_worktree_and_pushed_commit` show already-published commits can be rewritten locally, with remote untouched.
- Existing safe path is two-phase and should follow the squash: `POST /api/git/{project}/push/prepare` captures a fresh `PublishSnapshot` for the rewritten current HEAD; display destination and old remote/local OIDs, then separately confirm via `POST .../push/publish`. Preparing before squash yields a stale-local snapshot.
- `leased_push::prepare_leased_push` resolves only the checked-out branch's configured remote/upstream and exact destination. `publish_leased_push` revalidates repository/root identity, branch/source OID, upstream config, and push URL; its single-ref libgit2 push uses a `+source:destination` refspec but negotiation requires exactly one expected destination, advertised remote OID == `expectedRemoteOid`, and local OID == `sourceOid`. This is the backend's exact-OID force-with-lease equivalent, not an unconditional force endpoint. Stale remote/local/config reject; remote hook rejection is surfaced; post-send uncertainty returns `unknown` and must be reconciled, not blindly retried. Ordinary `/api/git/push` remains fast-forward-only; `force: true` is rejected (`deny_unknown_fields`).
- `PublishSnapshot` is a serializable client-held/request-supplied DTO, not a persisted server receipt, authorization token, or durable pending-publication record. It binds source, branch, destination, expected remote OID, URL identity, and selected repository/root identity; the server rechecks it at publish. Credentials are fetched from `AppState.ssh_creds` for each route and never belong in the snapshot.

### REST, owner/root, and WebSocket routing
- `server/src/api/git.rs::{resolve_target_path,get_commit_message_route,edit_commit_message_route,prepare_leased_push_route,publish_leased_push_route}` establish the pattern: `project` plus optional `worktreePath` goes through `AppState::resolve_project_target`; a supplied `root` is re-discovered/validated by `resolve_git_request_root` (root ID, no path escape/aggregate root). The project is the server-side identity; a supplied worktree path is accepted only if it is a registered live worktree. Add the operation under the protected REST router (`router.rs` applies `auth::require_auth` to this route group).
- Existing message API: `GET /api/git/{project}/commit/{hash}/message` returns complete UTF-8 message, full branch, exact head OID. `POST` accepts `message`, `expectedBranch`, `expectedHeadOid`, optional `allowSignatureRemoval`, `worktreePath`, `root`; it trims only to test empty, preserves full body, and appends one LF iff absent. Log rows expose subject-only messages, not full bodies. Squash needs an explicit finalized full-message contract; do not build it from `GitLogEntry.message` if bodies must be preserved.
- Git mutation and leased-publication commands are REST, not WebSocket requests. `/ws` is a separate authenticated/origin-checked stream. Push progress is broadcast as `git:progress` through `BroadcastEventSink` and the WS pump; commit-message rewrite currently emits no progress event. No squash WS route/protocol addition is implied by existing patterns.

## API/design options within this slice
- Add one shared REST squash mutation for both UI callers; keep it local-only and return the existing `GitActionResult` shape (old/new target and HEAD OIDs, rewrite count, signature removal, blocked reason). This reuses clients' REST mutation model and keeps publish separate.
- Range request choice: explicit ordered selected OIDs lets the backend verify every commit is reachable and adjacency is exact (more payload, selection/order must be defined); inclusive oldest/newest bounds reduce payload (server derives the interval, but orientation and ambiguous merge paths must be specified). In either case require `expectedBranch` + `expectedHeadOid` and validate range against the captured branch before writing.
- Message choice remains open: accept the user's final full message (clear ownership, no hidden concatenation) versus backend-generated concatenation/default message (requires explicit separator/order/body rules). Commit author/committer metadata for the synthesized squash commit also needs a rule; existing edit preserves original author/committer and is not a squash policy.
- Preserve `allowSignatureRemoval=false` by default. Squash invalidates selected commit signatures and may invalidate signatures/mergetags in rewritten descendants; consent analysis must cover every rewritten object and mergetag parent remapping, not just the selected range.

## Existing test patterns and suggested checks (not run)
- Unit tests in `server/src/git/tests.rs` use real `tempfile` repos, Git CLI setup/oracle checks (`rev-parse`, `log`, `reflog`), plus direct git2 ODB fixtures for signed/malformed commits. Relevant precedents: `edit_commit_message_rewrites_older_commit_and_descendants`, `edit_commit_message_preserves_merge_commit_tree_and_ordered_parents`, `edit_commit_message_octopus_merge_preservation`, `edit_commit_message_allows_dirty_worktree_and_pushed_commit`, signature/mergetag tests, linked-worktree tests, stale-ref tests.
- API tests in `server/tests/git_commit_message_api.rs` build an in-process Axum router (`tower::ServiceExt::oneshot`, `no_auth` test app), JSON round-trip, then independently verify Git refs/tree/worktree. Publication API tests in `server/tests/git_leased_publish_api.rs` use a local bare remote, prepare/publish, and simulate independent remote/local advancement. Add coverage for >=2 contiguous commits; root and non-HEAD ranges; exact adjacency/order rejection; unchanged branch-tip tree and descendant trees; active operation, stale CAS, dirty worktree, signatures/mergetags; published range warning/publication not implicit; stale remote no-overwrite after squash.
- Relevant real commands: `cargo test --manifest-path server/Cargo.toml --lib git::tests::edit_commit_message`; `cargo test --manifest-path server/Cargo.toml --test git_commit_message_api`; `cargo test --manifest-path server/Cargo.toml --test git_leased_publish_api`. New squash unit/API tests should run by their test filter/target alongside these; none were run for this discovery.
