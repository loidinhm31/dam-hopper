## Findings

### F1 — High: frozen language-filter wire values contradict server/web
- **Plan:** `P/contracts.md:14` retains the existing enum and promises exact web-string synchronization; `P/parity-matrix.md:43` explicitly accepts `all/known/code/text`. Phase01 freezes this model before branches (`P/phase-01-shared-contracts.md:12-15`).
- **Supporting source:** `K/features/settings/SettingsModels.kt:31-41` has `all/known/code/text`; actual web `packages/ui/src/api/fs-types.ts:123-127` and server `server/src/config/schema.rs:1045-1053` allow only `all/rust/javascript-typescript/java`. `server/src/api/config.rs:295-297` deserializes the merged UI into that enum.
- **Failure scenario:** Android saves an existing `code`, `known` or `text` filter through the newly synchronized field: server rejects the UI patch. Conversely, a web `rust` filter cannot decode into the retained native enum without a newly specified mapping/fallback. Dirty-field projection avoids harming unrelated saves, but cannot make this field interoperable.
- **Impact/severity/confidence:** High correctness/parity blocker; high confidence in schema mismatch. Exact hydration failure depends on chosen decoder, not observed execution.
- **Smallest correction:** Freeze the actual four wire values and real native language-family consumers; explicitly migrate/dispose legacy native `known/code/text` without inventing equivalence. If those local modes remain, separate their local authority from the shared wire enum. Update C1, S21, Phase01/02/04 requirements and qualification examples together. Add future decode/save tests for each real wire value and each legacy value.

### F2 — High: no owned dispatch-boundary mechanism can enforce C2 after credential suspension
- **Plan:** `P/contracts.md:53-59,82-84` exposes a raw `SettingsBinding.client` while promising fresh selection/edit/operation validation after every suspension, before dispatch. Phase02 repeats this (`P/phase-02-settings-parity.md:11,49-55`), but no task owns `ApiClient.kt` or an equivalent guarded transport boundary.
- **Supporting source:** `K/core/transport/ApiClient.kt:148-160,168-180,188-200,247-259` checks connection ownership, then suspends in `authTokenProvider()`, then submits HTTP with no intervening Settings-operation validation. Its registry guard (`:291-292`) knows generation, not independent Settings selection/operation revisions. Existing Settings selections themselves do not retire connections (`K/features/settings/SettingsRepository.kt:101-120,155-158`).
- **Failure scenario:** Capture destructive reset/import/config operation for target A; credential acquisition suspends inside `ApiClient`; user changes Settings target A→B→A. The same connection remains current, but the original operation is invalid. Returning credentials can still dispatch that old mutation. Rejecting its response afterward cannot undo the server mutation. Profile retirement during the same suspension similarly lacks a second pre-request generation check.
- **Impact/severity/confidence:** High stale-destructive-dispatch risk; high confidence in the source gap and current write-set insufficiency. This is a plan implementability gap, not a claim that future code already fails.
- **Smallest correction:** Define a narrow existing-transport guarded-dispatch contract accepting the captured operation validator, rechecked after credential acquisition and at request submission, with honest pre-submission versus possibly-dispatched outcomes. Allocate the exact transport/test files to one sequential owner and freeze the callback/signature before branches; carry it through all T/P mutations rather than a reset-only workaround. Do not introduce another client/runtime. Future regression: suspend credential provider, invalidate selection/owner, resume, assert **zero outbound requests**; separately retain Unknown for cancellation after submission.
