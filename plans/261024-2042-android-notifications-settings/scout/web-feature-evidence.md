# Web Settings and Notification Evidence

Read-only source map for Android parity planning. `apps/web` is a thin React host; UI implementation lives in `packages/ui`. No checks were run.

## Summary

- Web `/settings` is `SettingsPage` with eight accordions and two independent selectors: target server for workspace/config/maintenance operations; preferences source for shared UI settings, including notification policies. Agent path/integration management is **not** in this page: it is the Agent Store `/agent-store?tab=settings` tab. The terminal notification bell/history is a separate runtime UI.
- Web preference values (including v2 notification policies) debounce to selected server `globalConfig:updateUi` (`POST /api/global-config/ui`). Without a bound source, edits update the local offline snapshot; command history is explicitly browser-local; notification history/toasts are in-memory Zustand state.
- The current Android root is the guided login → project list → project workspace flow, not `WorkbenchScreen`. A separate retained Workbench shell contains `SettingsScreens` and `NotificationsView`, but is not mounted by `MainActivity`/`DamHopperMobileApp`. Android has notification sink and status-dedupe infrastructure, but source search found no live agent-event publisher to `postNotification`; `NotificationsView` only posts a synthetic test alert.
- Settled scope: port all Android-applicable web Settings categories/actions, not only appearance/preferences. Preserve native Compose and the current guided root (no WebView). Agent path/integration controls remain a separate server-host settings surface, as on web.
- Notifications are generated only from the app's live, connected runtime. “App running” is not a foreground-only promise: background delivery may occur while process and connection remain live, with no reliability guarantee. No new-delivery guarantee after process stop; push/FCM after stop is explicitly separate. Existing OS notifications may remain in Android's shade.
- Native Settings entry and live event-to-sink wiring are missing, despite retained components. Reuse server APIs; a parity design should map web toasts/history to native in-app UI, browser popups to Android system notifications/permission, and click routing to a current terminal owner. Preserve semantic agent rules (OMP + qualified Claude; Codex status-only), owner fencing and lock-screen redaction. Exact sound/popup mapping and UI placement are recommendations, not settled user decisions.

## Notification schemas and invariants

- Server-shared semantic event types (`packages/ui/src/api/agent-status-types.ts:10-68`): row `{id, incarnation, agentKind: omp|codex|claude, agentSessionId, reporterEpoch, state, source, attentionRevision, ...}`; attention `{id, kind: turn-ended|needs-attention, terminalId, incarnation, agentKind, agentSessionId, turnId?, reason: approval|question|error?, outcome?, attentionRevision, timestampMs}`; change wrapper `{serverEpoch, revision, row, attention?}`. Snapshot is version/epoch/revision/availability/rows.
- Web normalized event (`packages/ui/src/lib/terminal-notification-signal-parser.ts:5-40,47-115`): `{source: bel|osc777|osc99|quiet|tui-ready|terminal-exit|agent-status, sessionId, project?, agent, title, body?, status: needs-attention|finished|unknown, receivedAt, profileId?, terminalRef?, terminalInstanceRef?, semanticEventId?}`. Parser handles generic BEL, OSC 777 `notify`, and OSC 99; strips ANSI/control sequences and caps title/body at 80/180 chars. **No production caller of these parser functions was found under `packages/ui/src`; parser tests cover them.** Do not assume BEL/OSC currently deliver web alerts.
- Current production semantic path: `packages/ui/src/stores/agent-status.ts:113-188` → `deliverSemanticAgentAttention` (`packages/ui/src/lib/terminal-agent-notification-integration.ts:19-105`) → notification store, sound/browser services. `applyAgentStatusChanged` atomically records accepted revision/cursor, ignores duplicate connection revisions, rejects gaps/stale epochs and only calls delivery for attention with a newer terminal-local revision; `installAgentStatusSnapshot` is explicitly silent. The delivery function also rejects non-current connection and mismatched row/event terminal ID, incarnation, agent session, attention revision or agent kind (`:19-31`); requires policy version 2 and enabled agent. Codex emits status only (alerts return); Claude only `needs-attention`; OMP supports turn-ended and attention. Bodies are fixed reason labels; turn-ended explicitly says task success is unverified.
- Policy shape: `UiConfig.terminalAgentNotifications` v2, agents `codex|omp|claude`, each `{enabled, toast, browser, sound, volume, pattern}`; patterns `default|soft|two-tone|urgent` (`api/client.ts:2101-2122`). OMP enable also requires verified matching runtime/install paths. Claude path verification required. Permission request is explicit user-click, browser permission is runtime/site-level, not server config. Native’s unversioned model with `masterEnabled` and per-agent policy objects is not wire-compatible: preserve web v2 migration and unsupported-version no-overwrite behavior when synchronizing policy; keep Codex status-only and Claude qualified-attention-only.
- Store behavior (`packages/ui/src/stores/terminal-notifications.ts:5-90`): record ID uses `[profileId, semanticEventId]` for semantic events, duplicate history/toast entries skipped while ID remains in bounded 50-record history; other events get sequence IDs. Newest first, max 50 history / 3 active toasts. Toast-off still stores history. Read/clear/toast dismissal are independent except `clearNotifications` clears both. Store is in-memory, not persisted. This store dedupe alone does **not** suppress later sound or OS-notification side effects; those are gated upstream by accepted live status revision/cursor and silent snapshot handling above. Browser service (`packages/ui/src/lib/browser-notification-service.ts:50-119`) checks support/permission and defaults to 30s per terminal instance + source; semantic path sets `rateLimitMs: 0`, relying on upstream event acceptance.
- Click path: `TerminalNotificationCenter.tsx:12,64-68,122-135` and `TerminalNotificationToastViewport.tsx:28-45` mark read and dispatch `dam-hopper:terminal-notification-select` with session/profile/terminal/instance refs; browser popup `onSelect` uses the same dispatcher (`terminal-notification-navigation.ts:4-35`). `WorkspacePage.tsx:1444-1478` routes only if session is mounted and alive, or registered while status is loading; then focuses window, reveals/selects terminal and activates it. Avoid navigating a stale/unmounted terminal.
- Android contracts already available: `NotificationTarget(profileId, generation, serverEpoch?, terminalId?, incarnation?, attentionRevision?)`; `AppNotification(id, channel, target, title/body, publicTitle/body)` and channels TERMINAL_ATTENTION, TRANSFERS, IDLE_SUSPEND (`core/notifications/NotificationSink.kt:6-40`). `AndroidNotificationSink.kt:26,85` checks OS + Android 13 `POST_NOTIFICATIONS`, uses private lock-screen visibility with generic public version, and places target fields in immutable `PendingIntent`; it exposes profile cancellation. The observed retirement caller is `WorkbenchScreen.kt:932-934`, which is retained/unmounted, not active-root wiring. `MainActivity.handleDeepLink` (`MainActivity.kt:273-296`) reads profile ID/generation; if a current connection exists it rejects a generation mismatch, then selects profile. It does not route to terminal or validate server epoch/incarnation/revision. Preserve that partial guard; validate exact owner and generation again when deferred navigation executes after the departure guard, since reconnect/profile switch/terminal replacement may happen meanwhile.
- Native reducer (`AgentStatusReducer.kt:71,152-154`) epoch/revision-fences status, dedupes attention IDs in bounded 1,000-entry set and seeds historical snapshot attentions; this currently creates unread agent-status state, not OS notifications. New native notification side effects should occur only for newly accepted live attention events, never replayed snapshots or recomposed unread state. Native prefs use `TerminalAgentNotifications(masterEnabled, omp, claude, codex)` with per-agent `{enabled,toast,sound,browser}` only—no web sound pattern/volume (`SettingsModels.kt:62-84`). `NotificationsView.kt:330-345` can post only a synthetic test alert; its `Browser` checkbox has no browser engine, so map/replace explicitly rather than copying that label.
