# Client authentication integration inventory

**Research date:** 2026-09-26. **Scope:** requested shared UI entry files and directly relevant status/test surfaces; read-only source review.

**Synthesis:** [security contract](../security-contract.md) now defines HTTP states and WS close codes; [Phase 04](../phase-04-profile-mfa-flow.md) supersedes the initial recommendation to keep the old connection open. Retire the stale transport but retain the restricted bearer for step-up; successful verification recreates the transport with replacement credentials and unchanged absolute expiry. Android Chrome auth-entry interaction remains a validation topic.

## Recommended client integration points

1. **Enrollment (first password login for new and pre-existing accounts):** extend `ServerSettingsDialog.testConnection()` response state machine. Before accepting `{token}`, handle server “enrollment required” response; render QR and the identical manual setup key, collect a TOTP confirmation, and only treat the login as successful/store a usable token after server confirmation. Keep secret/challenge in ephemeral component state; never put setup secret in `ServerProfile`, token storage, or URL. Place enrollment and OTP controls alongside username/password and “Test connection” result, before `handleSave` can pass its `testState === "ok"` gate. Current login handler immediately expects a token and has no enrollment branch. [handler](../../../packages/ui/src/components/organisms/ServerSettingsDialog.tsx#L161-L216) · [form location](../../../packages/ui/src/components/organisms/ServerSettingsDialog.tsx#L695-L785) · [save gate](../../../packages/ui/src/components/organisms/ServerSettingsDialog.tsx#L827-L851)
2. **Password → challenge-only TOTP:** use the same request/result handler: password success with an MFA challenge must not populate `token` or enable Save; retain only a profile-qualified, short-lived challenge in memory, show the OTP field, and submit OTP to finish authentication. Wrong/expired challenge leaves token absent and provides a retryable error. Existing entered password is not persisted; do not create a new local credential convention.
3. **10-day step-up:** add a distinct step-up state/prompt in the authenticated request path (`ws-transport.ts` response/error dispatch) and render it in shared app/profile UI. Scope prompt and completion to captured `{profileId,generation}` (reuse `ConnectionRef`, invalidation and current-owner checks); ignore completion after profile switch, reconnect, deletion, or generation change. **Do not** map step-up to existing `login-required`, clear the stored still-valid 30-day session token, disconnect, or mint a new 30-day deadline. Client requires a distinguishable server signal; ordinary 401/403 currently means full login-required in connection preflight.
4. **30-day expiry:** retain the existing `/api/auth/status` 401/403 → `login-required` route as the full fresh password+TOTP path, not as the 10-day step-up path. After successful full auth, save the returned token only against the matching profile, then reconnect that profile. On bootstrap, rejected pre-rollout tokens must end in this login-required path rather than being treated as authenticated. `ServerSettingsDialog` already disconnects/reconnects after saved token changes; keep that behavior profile-local. [status path](../../../packages/ui/src/api/connections.ts#L362-L393) · [token-change reconnect](../../../packages/ui/src/components/organisms/ServerSettingsDialog.tsx#L367-L377)
5. **WS expiry:** distinguish an auth-expiry close from network close before letting generic offline retry spin against an expired token; surface the profile-owned full-login or step-up prompt according to server-provided cause. Current generic close/drop route does not itself show auth UI. Keep the 30-day hard-expiry outcome separate from day-10 step-up.

## Consumer-visible acceptance scenarios

- Fresh basic account and existing pre-rollout basic account both must enroll: setup screen shows scannable QR and exactly the same plain-text key; neither gets an authenticated session before valid enrollment confirmation.
- Successful password check produces an OTP challenge, not a JWT; valid TOTP alone completes login. Invalid/expired OTP leaves session/token absent; correct retry can finish.
- A profile without a token or with a rejected pre-rollout token reports Login required and requires password + fresh TOTP; `none` dev profile behavior remains explicit and isolated.
- At day 10, server advances the session credential version and issues a refreshed profile-scoped credential, preserving the Mongo-backed session identity and original fixed day-30 expiry. Client rotates the token-bound transport as required without treating it as logout or clearing viable session/resource state; the refreshed credential must not extend expiry. At day 30, require fresh password + TOTP.
- During profile switch, deletion, reconnect, or newer connection generation, late enrollment/OTP/step-up results cannot update or authenticate another profile; independent profile status/token remain unchanged.
- Browser and native shells use identical shared flow. Verify Android Chrome text-entry policy does not make mandatory authentication impossible.

## Blockers / assumptions

- UI response schema/endpoints and WS close-code semantics for enrollment, OTP challenge, step-up, and full expiry are not present in the inspected client contract; coordinate with server/transport research before wiring. Distinct step-up vs full-auth signals are mandatory to preserve the 30-day session.
- Recovery is operator-only via direct MongoDB edit per requirement; no recovery-code feature/UI/endpoint assumed.
- Exact parent wiring for `ServerProfilesDialog.onLoginProfile` is outside the inspected target set; current settings dialog is the only password-login consumer found in requested files. Confirm its existing login entry invokes the right profile-scoped instance when integrating.
