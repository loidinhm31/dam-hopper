# Host-resource SSE — architecture and implementation status

**Status:** Frozen end-to-end design contract, 2026-09-29; Phase 01's shared backend snapshot publisher is implemented. The authenticated SSE route, response-body admission/lifetime, frontend coordinator/cutover, and performance qualification remain later work; Phase 01 adds no HTTP endpoint. Current behavior remains the protected cached REST snapshot (`GET /api/system/resources/v1/snapshot`), legacy metrics (`GET /api/system/metrics`), alert history (`GET /api/system/resources/v1/alerts`), and WS host alerts. The design replaces **both** resource/metrics polling for supported visible clients only after healthy stream cutover. It adds no new monitor, generic event bus, host mutation, persistence, or settings UI, and leaves existing WS alerts/history, idle-suspend action authorization, and all host-action boundaries intact.

This is the target end-state flow, not an end-to-end shipped path. Phase 01 implements the monitor-owned cache pair/revision and feature-local frame publisher only; the response bodies, route, client coordination, and cutover below remain integration contracts.

## Phase 01 backend publisher contract (implemented)

`HostResourceMonitor` owns the shared cache and revision:

- `CachedHostResourcePair` contains `server_epoch`, `revision`, the full cached `HostResourceSnapshotV1` and `HostMetrics`, both successful-observation `Instant`s (optional for snapshot and metrics), and active `light_sample_ms`, `snapshot_deadline_ms`, and `jitter_ms`. Async `HostResourceMonitor::read_stream_pair(&self) -> CachedHostResourcePair` clones both projections and their metadata under one cache read lock; the publisher does not combine separate REST accessors.
- `StreamStatusBasis` contains only epoch/revision, observation instants, and freshness inputs. Async `HostResourceMonitor::current_status_basis(&self) -> StreamStatusBasis` copies these scalars under one cache read lock, without cloning either projection. Its `freshness_ttl_ms()` uses saturating arithmetic for `2 × (light_sample_ms + snapshot_deadline_ms + jitter_ms)`.
- Each committed observed/degraded update increments the revision once. A change to the clamped freshness inputs also commits one metadata-only revision, retaining the cached data and observation instants; applying unchanged effective freshness inputs adds no revision. Initial revision is zero. Revision is scoped to a random epoch; on `u64` overflow the monitor starts a new UUID epoch at revision zero. Status reads do not create revisions.
- Initial deep-snapshot observation is absent until a successful snapshot; initial legacy metrics are sampled synchronously and have an observation instant. A degraded deep sample retains the last successful snapshot instant while a successful legacy sample updates the metrics instant.

`HostResourcePublisher` is cloneable around one shared publisher state. Its contract is `new(monitor: HostResourceMonitor) -> Self`, `start(&self)`, `subscribe(&self) -> StreamSubscription`, async `current_status_basis(&self) -> StreamStatusBasis`, and async `shutdown(&self)`. Call `start()` to launch its feature-local task; it is idempotent. `subscribe()` registers interest and wakes the task. `shutdown()` cancels it, waits up to two seconds, then aborts it if needed. This is a publisher seam, not an HTTP handler or authentication boundary.

- The task encodes only while at least one subscription is interested. It publishes a latest-only watch value containing either one shared `Arc<PublishedFrame>` or `FrameTooLarge`; slow readers may skip intermediate revisions. All readers of a publication share the same `Bytes` frame. When interest drops to zero, no new frames are encoded; a stale retained publication is invalidated when the monitor revision has advanced.
- Async `StreamSubscription::latest(&mut self) -> Result<Arc<PublishedFrame>, FrameTooLarge>` returns the current watch publication; async `changed(&mut self) -> Result<Arc<PublishedFrame>, FrameTooLarge>` waits for a publication whose `{ server_epoch, revision }` differs from the last one returned. Both can skip intermediate revisions. Dropping the subscription releases its interest and wakes the publisher.
- `PublishedFrame` carries the complete pre-encoded data event plus its epoch/revision, captured observation instants, `light_sample_ms`, and revision-bound `freshness_ttl_ms`. `encode_data_frame()` writes the `host-resources` SSE event with schema version 1, decimal-string revision, snapshot, metrics, and light cadence; the complete event including framing is limited to 262,144 bytes. Oversize is a typed `FrameTooLarge` error carrying epoch, revision, reported frame size, and limit; no partial frame is published.
- `encode_status_control()` builds status from `StreamStatusBasis`; `encode_status_control_for_frame()` uses a selected frame's captured metadata. `encode_control_event()` and `encode_error_control()` bound the complete control event including framing to 4,096 bytes. The publisher returns a typed oversize outcome; later HTTP integration decides the finite response or post-header error behavior.

`server/src/system.rs` exports the monitor pair/status types, publisher/subscription/frame types, encoders, and size limits for later integration. See the [Phase 01 plan](../../plans/260929-1522-host-resources-sse/phase-01-shared-snapshot-publisher.md) for scope and implementation record.

## Target ownership and source of truth

```text
one server-started HostResourceMonitor -> one atomic cache pair + revision
  -> one feature-local, demand-driven bounded encoder -> latest pre-encoded watch frame
  -> at most 32 admitted authenticated response bodies (at most 4 per subject)
  -> one stream coordinator per connected ConnectionRef + QueryClient
  -> exact owner snapshot AND metrics TanStack keys -> fleet/detail presentation
WS host alert feed -> validated notification/unread + REST history (not live resource cache)
```

- The monitor collects independent of readers, even at zero SSE subscribers; no subscriber-driven Linux reads, faster cadence, new sampler, concurrent retry worker, or alteration to alert classification. Configuration is server-owned and clamped: light 1–60 s (default 5), processes 5–300 s (default 15), PSS 15–600 s (default 60), jitter ≤1,000 ms (default 250), process deadline default 150 ms, snapshot wait default 500 ms. A wait deadline does **not** bound host CPU or cancel a blocked syscall. The constructor currently samples legacy metrics synchronously; `sample_legacy` has no wait deadline. SSE must not conceal either behavior with extra workers. Source: [`monitor.rs`](../../server/src/system/monitor.rs), [`config.rs`](../../server/src/system/config.rs).
- Monitor `update` commits snapshot, `HostMetrics`, alerts, revision, active clamped freshness configuration and independent last-successful-observation `Instant`s under one cache lock on observed and degraded paths. A changed **actual clamped freshness configuration** makes an atomic metadata-only pair commit with **one new revision**, reusing the same snapshot/metrics/alert values and both observation instants: no collection, fabricated success or alert transition. Unchanged effective configuration makes no revision. Random `serverEpoch` identifies a revision epoch; the initial pair starts at revision zero. Each later data/degraded/config commit increments once; status ticks, heartbeats and failed uncommitted collections do not. On `u64` overflow the monitor creates a new epoch and resets revision to zero. The publisher reads the paired cache only while interested; it performs no reader-driven Linux work.
- Publisher owns one feature-local task and a latest-only `tokio::sync::watch` of a shared immutable frame record: pre-encoded data `Bytes`/`Arc`, its `{ serverEpoch, revision }`, and that **same pair's** captured observation metadata and active freshness configuration. Subscribers clone only the shared handle. While interest exists encode at most once per published revision, coalescing intermediate commits while busy; the per-client **small status control** is encoded separately at emission, never reserialize/deep-copy snapshot JSON per client. With zero interest retain at most one encoded frame record, perform **no new encoding** or serialized backlog even if the monitor commits, and drop any older record on demand if its revision is no longer current. On next interest reuse a matching current-revision record; otherwise the one publisher encodes the latest cached pair once. Do not release and re-encode an unchanged revision. No cache/watch guard across serialization, awaits, socket writes or subscriber callbacks. Subscribers borrow-and-update briefly, send current frame explicitly on subscribe, then observe `changed`; recheck revision to avoid duplicate bootstrap or lost wakeups. A slow subscriber skips intermediate frames (not already-buffered bytes); no per-subscriber producer/JSON/deep copy.
- The complete encoded **data event** (event name, JSON data, framing) is capped at 256 KiB. Use a bounded `serde_json::to_writer`-style sink (limit before extending its buffer), then append SSE framing within the same limit; avoid first allocating an unbounded JSON string. `Body::from_stream` with the project's existing re-exported `Bytes` can send shared frames without `axum::response::sse::Event::data` copying per client; no new crates. Oversize is never truncated: publish a bounded `FRAME_TOO_LARGE` error control and revoke/close current streams; return **503 JSON** `{ "code": "FRAME_TOO_LARGE", "error": "<safe reason>" }` before headers on a new admission if the latest cached pair still exceeds the frame limit. Recheck the latest revision before this decision; a later monitor revision may fit. This code, including HTTP 503, is **sticky REST-only for that connection generation**, not a transient 5xx retry. Alerts and monitoring continue. Bound the **entire encoded status/error control event including framing** to 4 KiB with a bounded sink and bounded safe reason; controls never contain snapshots. Keepalive comments are fixed and small.

## HTTP and wire contract (later-phase integration)

- New **GET** `/api/system/resources/v1/events` on the existing per-profile HTTP server. No profile ID in wire route/target, no new token, cookies, mutation, query-token, event ID, replay buffer or `Last-Event-ID` dependency. Browser uses authenticated `fetch` streaming with captured `Authorization: Bearer <token>`, `credentials: "omit"`, `cache: "no-store"`, `redirect: "error"`, and `Accept: text/event-stream`. Native `EventSource` cannot set Authorization. Return `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: private, no-store, no-transform` (sensitive host information; neither private nor shared caches may store it), `X-Accel-Buffering: no`; no HTTP/2-invalid `Connection` header. Disable compression/transform and buffering at each proxy, ensure proxy idle-read timeout ≥45 s. No proxy behavior is assumed qualified.
- On authenticated admission send an initial **status control** immediately, then the latest cached full pair (after first-demand encode if needed), before awaiting the next revision; send status at least every 15 s and on no-sample/unchanged conditions requiring freshness notice. An initial snapshot can be old or `unavailable`: neither `200`, status, nor heartbeat asserts fresh host data. Initial status may name a newer revision than the data frame selected later, so it is not automatically consumed for data. **Immediately before every data event**, after selecting that immutable frame and after any wait/backpressure, calculate and enqueue a small status for **that frame's captured revision and successful-observation monotonic metadata**, using the server's monotonic clock at actual emission, then enqueue its data event as the next event without an interleaved status/heartbeat. Do not read the current cache revision to label the selected frame; prior status or a newer periodic status must never freshen older data. Emit a `: keepalive\n\n` comment as transport-only heartbeat within 15 s if no other bytes. Status/heartbeat must never invoke sampling.
- Each `event: host-resources` carries one compact JSON object with **exact top-level fields** `{ "schemaVersion": 1, "serverEpoch": "<random UUID>", "revision": "<decimal u64>", "snapshot": <HostResourceSnapshotV1>, "metrics": <HostMetrics>, "lightSampleMs": 5000 }`. Snapshot and metrics preserve their existing full JSON contracts, including `snapshot.currentAlerts`. `lightSampleMs` reflects actual clamped active light interval at this revision. Server only sends complete current-state records, no deltas; fast commits can be skipped. On reconnect the latest complete state replaces older state even if revisions skipped. No SSE `id:` field, no assumption of replay.
- `event: host-resources-status` JSON: `{ "serverEpoch": "...", "revision": "<decimal u64>", "snapshotAgeMs": null | 0, "metricsAgeMs": null | 0, "freshnessTtlMs": 11500 }` (example ages; actual nonnegative monotonic milliseconds). Pre-data status uses selected immutable frame's epoch/revision, observation instants **and revision-bound TTL configuration** and computes ages at emission. Periodic status uses `current_status_basis()` (metadata-only async read: epoch/revision/observation instants/clamped TTL configuration) to describe latest server state, which may be ahead of a slow reader's data; it must not call `read_stream_pair()` or clone either full projection per subscriber. No freshness-config change can give one revision competing TTLs: changed config commits a new revision even without a successful sample. Age never resets on degraded timestamps, serialization or heartbeat; null means never observed.
- Finite errors before headers use JSON `{ "code": "...", "error": "..." }`; `FRAME_TOO_LARGE` uses HTTP **503**, distinct from retryable 5xx by its code. After headers, best-effort bounded `event: host-resources-error` JSON `{ "code": "MFA_REQUIRED|AUTH_REQUIRED|AUTH_UNAVAILABLE|FRAME_TOO_LARGE", "error": "<safe reason>" }`, then revoke emission and end the body; a blocked socket may never receive that control or EOF, and already-queued TCP/proxy bytes cannot be recalled. Explicit unavailable/stale status continues for a stalled sampler rather than synthesizing healthy commits. EOF without a recognized control is a transient transport failure, not proof of authentication failure.

## Admission, auth, shutdown and lifetime

- Only the feature route has admission/auth layers, beside protected REST. Effective GET order: existing outer CORS -> global permit (32, before auth) -> explicit present-Origin admission -> feature auth stage (2 s) -> bearer-mechanism guard -> per-subject permit (4; dev actor `dev-user`) -> handler. Route layering is reverse-wrapped; test constructed router. `OPTIONS` never consumes permits/reads auth: configured allowed-origin CORS preflight returns configured headers before feature middleware; with `allowed_origins` empty, no CorsLayer is installed and normal GET-only route `OPTIONS` returns 405 (no invented preflight grant). Present disallowed/multiple/malformed Origin returns 403 JSON before DB; absent Origin requires valid bearer outside explicit no-auth mode.
- Extract one shared `authenticate_request(&AppState, &CookieJar, Request) -> Result<Request, Response>` authentication/policy function from existing `require_auth`: only after successful policy insert actor, mechanism and verified full claims. Existing REST `require_auth` invokes it then runs `Next`; feature auth layer calls it once with `tokio::time::timeout(2 s, ...)`, **then** calls `Next` outside timeout. Do not wrap `require_auth`'s existing `Next.run`: publisher encoding/first-frame delays must never be mislabeled auth failures. Timeout drops the auth future and returns exact **503 JSON** `{ "code": "AUTH_UNAVAILABLE", "error": "Authentication backend unavailable" }`; no headers/stream and global reservation released. Completed auth-store unavailability retains existing coded 503 (clients use the code; raw diagnostic details must not be added). Authentication admission cap does not bound publisher first-demand encode or OS sampling.
- Global pre-auth guard inserts `AdmissionPermit(Arc<Mutex<Option<OwnedSemaphorePermit>>>)` into request extensions (`http::Extensions::insert` requires `Clone + Send + Sync`); downstream `take()` transfers the unique owned permit into `BodyLease` together with the verified subject slot. Cloned extensions share one Option, never mint permits; error, timeout and Drop release once, not at handler return. A consumed permit cannot be taken again. Subject map drops zero-count entries. Independent live-body supervision retains complete signed claims, never bearer text.
- Revalidate long streams in an **independent supervisor**, not inside body polling (a backpressured body might not be polled). At admission retain verified signed `AuthClaims` (`v`, `sub`, `sid`, `authVersion`, `credentialVersion`, `iat`, `exp`) in nonsecret request extensions; never retain bearer token. Today `AuthenticatedActor` lacks `iat`, so reconstructing claims from actor alone is incorrect. Supervisor uses `AuthService::evaluate_claims(&claims)` (session **and user lookup**, 2 DB reads/check, same MFA/expiry/revocation/version policy); once every 5 s wrap persisted check in a 2 s timeout and fail closed on unavailable, expiry, revocation or MFA requirement. Also arm an independent deadline for earliest already-verified MFA/absolute expiry: stop at deadline even if no DB tick or body poll. Verified actor's subject/session/versions/deadline can bind the supervisor but never replace complete signed claims/policy. Publish a small authorization lease/cancellation state; independently **revoke eligibility to emit** on failure, without waiting for a backpressured body to poll. Each emission checks valid lease **after every await** and immediately before yielding each frame, including initial data, paired status and heartbeat; on failure stop eligible delivery first, then best-effort error control and body termination when writable. Neither an error control nor wire-close is guaranteed under backpressure; already-queued TCP/proxy bytes cannot be recalled. The 5 + 2 s check is an application scheduling goal, not a delivery/recall guarantee. At N=32, 2N/5 = **12.8 DB reads/s**, plus new admission and existing WS checks. No DB read per event/heartbeat.
- Body Drop cancels supervisor and releases permit/subject count exactly once. On shutdown signal, start global **10 s deadline immediately** and revoke feature emission/new admissions before Axum graceful drain; feature publisher/supervisor cleanup owns a **≤2 s** deadline and aborts/reaps laggards. Narrow `server/src/http_shutdown.rs` binary module wraps existing Tokio `TcpListener` as Axum 0.8.8 `serve::Listener<Io = ForceCloseIo, Addr = SocketAddr>`. In `main.rs` pass `ForceCloseListener.tap_io(|_: &mut ForceCloseIo| {})` using `serve::ListenerExt`: this deliberate **zero-work type adapter** selects Axum's installed generic `Connected<IncomingStream<'_, TapIo<L,F>>> for L::Addr`, which preserves actual remote `SocketAddr` via `remote_addr()`; direct `impl Connected<IncomingStream<'_, ForceCloseListener>> for SocketAddr` is illegal Rust orphan impl. Retain `router.into_make_service_with_connect_info::<SocketAddr>()`. Per accepted stream clone one global force `CancellationToken` into **separate pinned owned cancellation futures for read and write halves** (write/flush/shutdown share write waiter); check `is_cancelled()` and poll the proper waiter before delegating each `AsyncRead::poll_read` / `AsyncWrite::{poll_write,poll_flush,poll_shutdown}`, returning `ConnectionAborted` on force. Independent waiters retain both wakers if upgraded WS splits read/write across tasks; no extra I/O task. Timer cancels force at signal+10 s independent of feature cleanup or Axum drain; blocked socket polls wake, accepted HTTP/WS connection tasks finish and `serve.await` reaches existing later idle-suspend/monitor/tunnel/telemetry/PTY cleanup. Test simultaneous blocked read/non-reading backpressured write and split WS sides, plus peer ConnectInfo. Dropping outer `serve` future alone does not stop spawned connection tasks; neither revocation nor force cancellation promises peer EOF/control delivery or recalls buffered bytes. HTTP drain bound is **not whole-process termination**: existing blocked collector or later cleanup remains separate.

## Browser coordinator and source arbitration

- `WsTransport` owns profile-bound authenticated fetch, a bounded ≤4 KiB finite-error parser and idempotent fetch+reader cancellation, not retries. Its transport result is `{kind:'stream',response,reader,close}` (non-null readable/cancellable body), `{kind:'finite',status,code:string|null,retryAfter:string|null,close}` or `{kind:'unsupported',close}` (owner-native streaming missing or 200 without actual readable/cancellable body); invalid/missing SSE content type **with** readable body is transient protocol error, not unsupported. It alone maps recognized 401 `MFA_REQUIRED` to 4403 and `SESSION_EXPIRED`/`SESSION_REVOKED`/`AUTH_REQUIRED` to 4401, once per attempt; unknown 401/403 stays SSE-only. Exact 503 JSON `AUTH_UNAVAILABLE` or recognized error control sets persistent auth latch: synchronously fence/cancel **both** resource REST requests, block snapshot/metrics REST and retain WS/credentials. While visible expose mode `AUTH_BLOCKED` even during capped SSE auth-probe backoff/fetch, not `STARTING`; hidden mode `PAUSED` preserves latch and resumes blocked. Current authenticated paired full frame atomically promotes LIVE and clears latch, or explicit new connection generation clears it; status, ordinary REST success, rerender or visibility alone never do.
- Feature-local coordinator keyed by captured `{ profileId, generation }` **and QueryClient**; `connections.ts` starts only for connected supported profile, visible interested consumer. Fleet/detail share one stream; hooks never independently open stream. Native capability must be owner-bound authenticated-fetch-stream plus cancellation; otherwise `unsupported` gives sticky `REST_ONLY` for generation **unless auth latch already exists**, in which case keep `AUTH_BLOCKED`. Never ambient/global fetch bypass. Offline auto-connect profiles retain last known state, no requests. Token/endpoint/connection/removal/reset/pagehide changes abort body/reader/timers and fence late work; visibility resume only same owner/budget. Token rotation captures reconnect intent before `disconnectProfile` clears it, then new generation reconnects without old token.
- Seven coordinator modes remain `STOPPED`, `STARTING`, `LIVE`, `RETRY_WAIT`, `REST_ONLY`, `AUTH_BLOCKED`, `PAUSED`; history remains separate REST. Public local source snapshot `getHostResourceSource(owner, queryClient)` exposes `{ mode, sourceGeneration, switching: boolean, freshness }`. Shared `canUseResourceRest(owner, queryClient)` requires current owner/QueryClient, visible interested state, an allowed REST mode, `!switching` and `!AUTH_BLOCKED` latch; call it before every resource snapshot/metrics request, REST result write, WS patch/invalidation and catch-up. On valid full data, synchronously set `switching=true` and bump sourceGeneration **before awaits**, then cancel both exact-owner queries with propagated AbortSignals, batch both SSE cache writes, enter `LIVE`, clear switching only for the still-current attempt; stale completion cannot clear a later attempt's switch flag. On exit fence SSE before REST is eligible; coalesce one owner catch-up where permitted. Every async completion matches ConnectionRef, QueryClient, attempt and sourceGeneration; switching prevents all REST and WS writes/requests during handoff.
- Initial **data** deadline 10 s from fetch attempt; byte inactivity deadline 45 s, reset by actual body bytes (comments count as transport bytes only). Network error, EOF, HTTP 429/5xx except coded 503 `FRAME_TOO_LARGE`, bad protocol or timeout gets first attempt plus at most **five** retries with positive-jitter exponential base 1/2/4/8/16 s (cap 30 s); honor bounded `Retry-After` ≤60 s for 429. Do not reset failures until 60 s stable with advancing revisions; beyond budget REST-only for ordinary faults or remain `AUTH_BLOCKED` for auth unavailability until new generation/explicit reconnect. 404/405 and `FRAME_TOO_LARGE` are sticky REST-only. Explicit reconnect/new generation resets budget; rerender/visibility does not. SSE-only faults never disconnect profile WS or clear credentials.
- Parse SSE by bytes with streaming UTF-8 decoder, split CR/LF/CRLF, multiline `data:`, comments, blank dispatch; enforce complete data-event 256 KiB and status/error 4 KiB bounds including framing, not arbitrary chunk size. Validate named event, schema and canonical decimal-u64 revision via `BigInt`. Each data event requires fresh immediately adjacent matching epoch/revision status from **the current attempt**; initial full frame on a new attempt may equal the last revision from a prior attempt and establishes a new baseline, even after auth blockage when generation matches; deduplicate equal revision **within** the same attempt, reject regressions, and accept epoch change only from a valid paired full frame. Status without data never grants cache ownership.
- REST fallback cadence: snapshot 15 s for connected/visible interested owner; **visible detail** compatibility metrics 5 s (not current 1 s, which oversamples the default producer); hidden no resource polls. This is not an additional server collector. TanStack `isStale`/socket presence must not be used as evidence of sampler freshness; status uses monotonic age plus per-section availability. Preserve WS `host:alertChanged` validation and presentation unread/notification paths, and `host:alertsInvalidated` history invalidation. While SSE is healthy WS events **never patch/invalidate the resource snapshot or metrics**: cross-channel ordering could roll back the authoritative SSE alert array. On REST fallback resume WS's validated snapshot patch/invalidation and history. Remove any ambient/unqualified alert resource-cache write for SSE-owned qualified owners; no duplicate alert event channel.

## Qualification and rollout gate (later-phase targets; performance unqualified)

- Structural: same monitor collection frequency and number of collector workers at 0/1/4/16/32 clients; no per-client snapshot serialization, at most one cached encoded frame with zero readers, no new encoding while zero and unchanged-revision reuse upon renewed interest; a bounded ≤4 KiB per-client status control before every ≤256 KiB data frame; 32 global / 4 actor limits enforced including slow clients. Model only: 32 × 256 KiB / 5 s ≈ **1.6 MiB/s** global data payload at default cadence (configured 1 s up to 5×), **plus per-client small status controls**; OS/proxy buffers omitted.
- On a named reference host measure **incremental SSE** steady CPU ≤1 percentage point of _one core_ at 1 client, ≤3 points at 32; frame serialization p95 ≤5 ms; sample commit-to-UI p95 ≤1 s on loopback **excluding** collection/proxy; RSS at 32 after warmup ≤32 MiB above no-SSE baseline with ≤1 MiB growth in final 10 min of a 30 min run; after final disconnect tasks/permits/subject map return to baseline within 5 s (allocator RSS need not shrink). Whole-monitor independent target ≤2% one core at default cadence; if baseline fails, record and consider only existing server-owned cadence tuning after alert review. Do not silently change thresholds after failure.
- Prior **collector-only** local evidence: ten full scans mean 47.075 ms CPU, max 48.262 ms CPU, peak 7,505-byte deep snapshot, 518 PIDs, zero deadlines. It excludes legacy sampling, JSON, fanout, auth, proxy and browser; it is not SSE/whole-monitor qualification. `docs/system-architecture.md` elsewhere mentions a 100 ms process budget; actual clamped default config's 150 ms process deadline is normative. See [collector profile](../../plans/260929-1522-host-resources-sse/research/local-collector-profile.md).
- Qualify Origin/OPTIONS configured vs empty, auth admission 2 s exact coded 503, cloned-extension one-shot permit, independent expired/MFA/DB supervision with unpolled body, 32/4 body lifetimes, oversize, zero-reader reuse and changed-config metadata-only revision/unchanged config, paired status/slow reader, browser switching/auth latch/reconnect equal-baseline, REST/WS races. Test actual non-reading socket filled to backpressure and signal: feature emission revoked immediately, feature tasks stopped ≤2 s, **all accepted HTTP/WS connections** forced I/O cancellation by signal+10 s, Axum serve drain finishes and later PTY cleanup remains reachable. Do not interpret ten collector scans as whole-monitor qualification; actual browser, DB and deployment proxy gates remain pending.
