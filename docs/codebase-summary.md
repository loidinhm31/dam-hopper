## Android Native Client Map (`native/android-app/`)

The Android client connects to the existing remote Rust backend through Kotlin Multiplatform and Jetpack Compose. Its root route stages remain Profile Login → Project List → Terminal, and the Terminal stage now mounts focused Terminal/Files/Editor/Git panels (`WorkspacePanel.GIT`) through retained per-owner workspace state. Phase 05 supplied the Android editor bridge; Phase 06 completed save/mutation integration; Phase 07 integrated retained workspace state; the Focused Git View increment landed safe Git operations directly into the focused workspace. All 1,168 automated unit tests are reported passing (937 shared JVM + 231 Android unit tests, 0 failures), and Cycle 3 code review reports 0 Critical issues remaining. Connected device qualification remains open (GATE-C). See [Android Native Client Architecture](./architecture/android-native-client.md).

## Current Architecture and Invariants

- **Multi-Profile Workbench:** Profile management is client-side; connections, transports, QueryClients, and state are scoped to `profileId` and connection generation. Server-owned project, PTY, workflow, and filesystem data remain on the owning server.
- **Authentication & Backend Selection:** SQLite is the default authentication store when unconfigured (`DAM_HOPPER_AUTH_SQLITE_PATH`, default `auth.db` in the global config directory; one server process per local auth file, no network/shared filesystems). MongoDB is selected automatically when both `MONGODB_URI` and `MONGODB_DATABASE` are configured, enforced via `DAM_HOPPER_LITE_MODE=false/0`, or SQLite forced via `DAM_HOPPER_LITE_MODE=true/1`. Unreachable or failing MongoDB fails startup without SQLite fallback. Production authenticated mode requires a dedicated 32-byte owner-only `DAM_HOPPER_MFA_KEY_FILE`. Public registration API is removed for security; administrator accounts are provisioned offline directly via `scripts/create-admin.mjs`; `--no-auth` is a separate loopback development bypass. See [Server Environment and Authentication](./configuration/server-environment-auth.md) and [Authentication API](./api/authentication.md).
- **Git Safety:** Commit message rewrites and squashing operate on active or inactive local branches via branch-qualified snapshots and ref compare-and-swap (CAS). Publication uses exact expected-OID leases bound to the target branch (`PublishSnapshot`).
- **Tunnel Lifetime & Reminder:** Cloudflared quick tunnels remain config-isolated (`--config ""`, `--no-autoupdate`) with localhost Host rewriting and single-authority supervisor exit. Explicit forwards survive origin/PTY loss and owner replacement, preserving PID/ID/URL/start time; Stop, connector exit, and server shutdown remain terminal. A server-owned monotonic three-hour deadline retains `reminderDue` in REST and emits one `tunnel:reminder`; profile/generation-scoped shared UI provides session Dismiss/Stop, no expiry. Untracked-origin rows stay visible; replacement services on the same port remain public.
- **Settings Default Collapsed:** Settings page sections (`SettingsSectionAccordion`) default to collapsed state (`defaultOpen = false`), leaving persistent server selectors uncollapsed.
- **Agent Status & Decoupled Session Changes:** Correlates terminal ID with PTY incarnation. OMP reports semantic status over private loopback WebSocket; Codex and Claude use protected Unix-socket hook ingress with peer-credential checks. In Phase 03 of the lightweight Session Changes refactor, the OMP Agent Status extension (`omp-agent-status.ts`) is strictly decoupled from Session Changes, isolated to execution states (`idle`, `working`, `blocked`, `unknown`), heartbeats, and notifications over WebSocket. The standalone tool-event producer asset `omp-session-changes.ts` hooks `tool_call`/`tool_result` (`write`, Hashline `edit`, concrete `ast_edit`) with 1500 ms fail-open capture targeting private HTTP endpoints (`/private/session-changes/v1/*`). In Phase 01, `server.session_changes_enabled` (default `false`, camelCase `sessionChangesEnabled`, snake_case TOML `session_changes_enabled`) provides the master configuration switch, gating all endpoints with HTTP 503 `trackingDisabled` and installing/removing `extensions/dam-hopper-session-changes.ts` independently from Agent Status via SHA-256 header validation and atomic writes. In Phase 02, the Rust backend delivers the lightweight per-file capture engine: replacing repository inventories and `AbsenceTrie` with metadata-only registration (`POST /register`), first-touch safe pre-edit capture (`POST /capture`, `mode: "preEdit" | "unproven"`), zero-diff settled turns (`POST /settled`) and status (`GET /status`, `POST /lookup`), lazy viewer-only file reads and line comparisons (`GET /files`, `POST /refresh`, `GET /files/{fileId}`), and strict resource bounds (2 MiB per file, 64 MiB global storage, 500 files per session, 32 sessions). In Phase 04 and Phase 05, `SettingsPage.tsx` delivers the target-server toggle (`targetOwner`) with active-OMP restart notices, trigger gating across UI components (`useSessionChangesEnabled`), lazy comparison bootstrapping, and `SessionChangesApp` / `SessionChangesHost` modal event containment (`stopPropagation()` on dialog content with OS-level input arbitration). ## Test and Deployment Boundaries

DamHopper enforces a **4-tier testing architecture** (see [Testing Guide](./testing.md)):
1. **Rust Backend Tests (`cargo test` / `pnpm test`):** Real temporary filesystems, Git ODB rewrites, CAS updates, PTYs, and API routes without synthetic mocks.
2. **Frontend Unit Tests (Vitest jsdom):** Headless unit tests under `packages/ui/src/**/*.test.{ts,tsx}`.
3. **Browser Component Regressions (Vitest Browser Mode):** Headless Chromium tests under `packages/ui/browser-tests/**/*.browser.{ts,tsx}` on ports 15173/15174.
4. **Application E2E Journeys (`@playwright/test`):** Full end-to-end browser journeys under `packages/ui/e2e/**/*.spec.ts` testing built web SPAs against production server containers (default MongoDB container or `authBackend: "sqlite"` without a MongoDB container) with deterministic auth seeding (`application_e2e_seed`).

Deployment artifacts are located in `deploy/release/` and documented in the [Installation and Deployment Guide](./deployment-guide.md).
